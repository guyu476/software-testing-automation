2代码和 Postman 是一回事

不是换工具，是把「点」变成「写」

你可能会觉得「学 pytest」是进入一个全新领域。其实你在 Postman 里已经把这四个动作全做过了，代码只是换一种写法：

你在 Postman 里做的 代码里对应的
填 URL、选 GET、点 Send requests.get(BASE_URL, params={"userId": user_id})
URL 里的 {{userId}} 环境变量 params 字典里的一个值
Tests 里写 pm.response.to.have.status(200) assert resp.status_code == 200
Tests 里写 pm.expect(jsonData.length).to.eql(10) assert len(resp.json()) == 10
导入一份 CSV 当测试数据 csv.DictReader 一行行读进来
Collection Runner 按行迭代 8 次 @pytest.mark.parametrize
报告里每条用例显示的名字 pytest.param(..., id="用例名")

四个动作一一对应，没有第五个。你写这一段代码的时候，心里可以一直念着「这行就是我在 Postman 里点的那个东西」。

那为什么还要学代码？

  • 能进版本库、能被人 review。Postman 的 Collection 是个 json 文件，改动看不清楚；代码改了哪一行，diff 里一目了然。团队协作时这是刚需。
  • 能和 CI 流水线接起来。代码可以被「提交时自动跑一遍」，Postman 的 Runner 做不到。
  • 能表达复杂逻辑。要加密签名、要连数据库核对、要处理多层嵌套的响应，用鼠标点不出来，写代码几行就完了。
  • 招聘要求里明写。「pytest + requests」几乎是接口自动化岗位的默认组合，比「会用 Postman」高一个档。

但不要说 Postman 没用。它擅长的是「接口还没定型时的探索和调试」——手工改参数、看响应、快速试。代码擅长的是「定型之后的批量回归」。面试时被问「你用 Postman 还是写代码」，正确答案是「两个都用，看阶段」，不是二选一。

3目录里的三个文件

D:\selenium\api-test\pytest\

文件 它是干什么的
posts_by_user.csv 测试数据。就是你 Postman 里用的那一份，内容一模一样，也放在同一个目录方便代码读取。
test_posts_by_user.py 测试代码。读 CSV → 发请求 → 断言。整个文件只有 1 个测试函数，但它会跑出 8 条用例。
pytest.ini pytest 的配置文件。目前只干一件事：让报告里的中文用例名正常显示，不要变成 \u6b63\u5e38 这种乱码。

为什么文件名必须有 test_ 前缀？这不是格式要求，是 pytest 的约定：它默认只收集文件名匹配 test_*.py 或 *_test.py 的文件，只把名字以 test 开头的函数当成用例。

所以你写了个普通脚本想跑，pytest 理都不理你——不是坏了，是你没按约定命名。

4逐行看测试代码

test_posts_by_user.py

— 开头：导入和常量 —

import csv
import pathlib

import pytest
import requests

BASE_URL = "https://jsonplaceholder.typicode.com/posts"

CSV_FILE = pathlib.Path(__file__).with_name("posts_by_user.csv")
  • csv —— 读 CSV 文件，Python 自带，不用装。
  • pathlib —— 处理文件路径。
  • pytest —— 提供 @pytest.mark.parametrize 这个「装饰器」。
  • requests —— 负责发 HTTP 请求，就是代码版的 Postman。

__file__ 是什么？它就是「当前这个 py 文件自己的路径」。with_name("posts_by_user.csv") 意味着「换成同一个目录下的这个名字」。

好处：不管你从哪个目录敲 pytest 命令，它都能找到那份 CSV。如果你写成 "posts_by_user.csv"（相对路径），那就必须站在这个目录里运行，换个地方就报「文件找不到」——这是新手最常见的坑之一。

— 读 CSV：把每一行变成一条用例的参数 —

def load_cases():
    cases = []
    with open(CSV_FILE, encoding="utf-8") as f:
        for row in csv.DictReader(f):
            cases.append(
                pytest.param(
                    row["userId"],
                    int(row["expectedStatus"]),
                    int(row["expectedCount"]),
                    id=row["caseName"],
                )
            )
    return cases

这段就是 Postman 的「导入 CSV」+「Runner 迭代」。逐点解释：

  • csv.DictReader(f) —— 把 CSV 按表头读成字典。表头是 caseName,userId,expectedStatus,expectedCount，于是每一行变成 {"caseName": "正常_有数据", "userId": "1", ...}。这样你就能用 row["userId"] 取值，不用记「第几列」。
  • int(...) —— 必须转，这是个坑。CSV 里读出来的东西全都是字符串。expectedStatus 读出来是 "200" 而不是 200。而 "200" == 200 在 Python 里是 False，断言会全红。所以这里转成整数。
  • id=row["caseName"] —— 报告里显示的用例名。不加这个，用例名会变成参数值拼起来的 userId1-200-10 之类，8 条看着一模一样，失败了你不知道哪条挂了。

— 测试函数：一个函数，8 条用例 —

@pytest.mark.parametrize("user_id, expected_status, expected_count", load_cases())
def test_posts_by_user(user_id, expected_status, expected_count):
    resp = requests.get(BASE_URL, params={"userId": user_id}, timeout=10)

    assert resp.status_code == expected_status

    assert len(resp.json()) == expected_count

这几行的意思：把 load_cases() 返回的 8 组参数，轮流喂给下面这个函数，跑 8 次。每次跑，三个参数的值都不一样。

拆开看：

  • @pytest.mark.parametrize(...) —— 上面那行带 @ 的叫装饰器，作用是「修饰」下面那个函数。这里的作用是：这个函数不要只跑一次，而是按我给的数据跑 8 次。这就是 Postman Runner 的迭代。
  • 第一个参数是字符串 "user_id, expected_status, expected_count"，三个名字用逗号隔开，名字随你取，但必须和函数括号里的参数名一一对应。
  • requests.get(BASE_URL, params={"userId": user_id}) —— params 会自动把字典拼成 URL 后面的查询串，拼出来就是 .../posts?userId=1，和你 Postman 里那个地址一字不差。timeout=10 是「超过 10 秒算失败」，好习惯，防止接口卡住时测试无限等。
  • resp.status_code —— 响应状态码，就是 Postman 里那个 200 OK。
  • resp.json() —— 把响应体解析成 Python 对象。这个接口返回的是数组，所以解析出来是列表，len() 就能数出条数。
  • assert 条件 —— 这是 Python 关键字，意思是「我断言这里必须成立」。成立就继续往下走；不成立就当场抛错，pytest 把这条用例标成 FAILED。这就是 Postman 的 Tests 断言。

一个函数 8 条用例，这就是 parametrize 的价值。以后要加 20 条 userId 的测试，你不用复制 20 份代码，只要在 CSV 里加 20 行。代码一个字都不用改。

— pytest.ini：那个名字很长的配置 —

[pytest]
disable_test_id_escaping_and_forfeit_all_rights_to_community_support = True

这个选项名的意思是「禁用测试名转义，并放弃一切向社区求助的权利」——pytest 作者故意起得这么长，因为关掉转义确实有风险：如果你的终端编码不支持中文，输出会真的乱掉。

本来的行为是：pytest 发现非 ASCII 字符（中文）就把它们转义成 \u6b63\u5e38，这样在任何古老终端上都不会崩。但你的用例名全是中文，转义之后就没法看了，所以关掉它。前面试过：不关的时候报告长这样——

关掉之前
test_posts_by_user[\u6b63\u5e38_\u6709\u6570\u636e]PASSED
关掉之后
test_posts_by_user[正常_有数据]PASSED

这个文件必须是纯 ASCII 内容、且不能带 BOM，否则 pytest 解析配置时会直接报错。真实项目里这种事很常见：一个看不见的字节就能让整个测试跑不起来。

5自己跑一遍

打开 PowerShell 或 cmd，敲这一行

— 完整命令（可直接复制）—

py -m pytest D:\selenium\api-test\pytest -v

解释一下这三段：

  • py —— Windows 的 Python 启动器，你机器上可用（已实测）。
  • -m pytest —— 意思是「用 Python 去跑 pytest 这个模块」。比直接敲 pytest 更稳，因为它保证用的是你装包的那个 Python，不会跑岔到别的版本上。
  • D:\selenium\api-test\pytest —— 告诉 pytest 去哪个目录找用例。给了绝对路径，你就不用先 cd 过去。
  • -v —— verbose，详细模式，每条用例单独列一行。不加的话只显示一串点，看不出哪条是哪条。

你会看到什么：先是 collected 8 items，然后 8 行 PASSED，最后一行 8 passed in xx.xxs。

如果 collected 0 items——那说明文件没被收集到，八成是文件名或函数名忘了 test_ 前缀。

故意跑一次失败的

把 CSV 里第一行的 expectedCount 从 10 改成 11，存盘，再跑一次。你会看到 pytest 告诉你：

assert len(resp.json()) == 11
E   assert 10 == 11
 +  where 10 = len([...])

这就是「应该的样子」和「实际的样子」并排摆给你看——你在这个项目里一直用的定位方法，pytest 自动帮你做了。看完记得把 11 改回 10。

6自测题（口述优先）

先自己说一遍，再展开看答案

试着不看文档回答

  2. 你的代码里只有一个 test_ 函数，为什么报告里跑出了 8 条用例？
  3. 如果删掉 id=row["caseName"] 这一行，会有什么变化？
  4. 现在要新增一条用例：「userId=5，期望返回 10 条」，你需要改哪个文件？要改代码吗？
  5. CSV 里读出来的 expectedStatus 为什么要 int() 一下？不转会怎样？
  6. 如果第 3 条用例断言失败，第 4 到第 8 条还会继续跑吗？
展开参考答案

1. pytest 是怎么知道哪一行是用例的？

靠命名约定，不是靠配置。默认规则两条：文件名要匹配 test_*.py；文件里的函数名要以 test 开头。两个条件都满足才会被收集成用例。

这也解释了为什么你写了个普通脚本 pytest 不跑它——不是没装好，是没按约定命名。

2. 一个函数为什么跑出 8 条用例？

因为 @pytest.mark.parametrize。它拿到 load_cases() 返回的 8 组参数，把这一个函数展开成 8 条独立用例分别跑。每组参数跑一次，互不影响。

对应到 Postman，就是 Collection Runner 拿着 CSV 迭代 8 次。

3. 删掉 id 会怎样？

用例名会变成参数值的拼接，类似 test_posts_by_user[1-200-10]。8 条看起来高度相似，一旦失败，报告里很难一眼看出是哪个 userId 挂了。

功能上不影响跑，只影响报告可读性。所以这是「该有的习惯」，不是「必须的语法」。

顺带一提：这也解释了为什么你那份 CSV 里要有 caseName 这一列——它不只是备注，它的作用就是喂给 id。

4. 新增一条用例要改哪里？

只改 CSV，代码一个字都不用动。在末尾加一行：

正常_第五条,5,200,10

再跑一次，就会变成 9 条用例。这就是数据驱动的核心价值，也是面试里最常被追问的点：数据驱动不是「用 CSV 存数据」，而是新增用例不需要改代码。

5. 为什么要 int()？

因为 CSV 读出来的所有字段都是字符串。expectedStatus 读出来是 "200"。

而 "200" == 200 在 Python 里是 False（字符串和整数不相等，且 Python 不会自动转换）。不转就会 8 条全红，而且报错信息是 assert '200' == 200，一眼看不出问题在哪。

这条是接口自动化新手的头号坑，记牢。

6. 一条失败，后面的还跑吗？

会继续跑。pytest 默认「失败不中断」——某条用例抛了断言错误，就把它标记成 FAILED，然后接着跑下一条，最后统一汇总。

这正是你想要的行为：一次跑完知道哪些挂了，而不是查到第一个问题就停下。Postman Runner 也是这个逻辑。

反过来说：如果一条用例失败导致后面全部跳过，通常是「前置步骤失败」，那是另一类问题（后面讲 fixture 时会碰）。

动手题
  1. 按上面第 4 题，在 CSV 加一条 正常_第五条,5,200,10，跑一遍，确认变成 9 条。
  2. 再加一条 异常_超范围,100,200,0，跑一遍。
  3. 把第一条的 expectedCount 改成 11，跑一遍，看清测试失败时 pytest 给你的报错长什么样，然后改回来。

这三步做完，你就把「数据驱动」和「断言失败怎么读报告」亲手摸了一遍，比看十遍文档有用。

7面试怎么讲这一块

把你的实操说成「做过的事」

被问到「有没有做过接口自动化」时，不要只说「学过 pytest」，要说出你解决过的具体问题。你这一讲里已经攒下了三个能说的点：

可以这样说 1 —— 数据驱动

「我用 pytest 的 parametrize 做数据驱动，把测试数据放在 CSV 里，一个测试函数覆盖了 8 条用例，包括正常值、边界值（userId=0、10）、异常值（负数、不存在、非数字）。新增用例只改数据文件，不动代码。」

可以这样说 2 —— 踩过的坑

「CSV 读出来的字段全是字符串，期望状态码如果不转成整数，"200" == 200 会是 False，导致用例全部误报失败。这个坑我踩过。」

这类「踩过坑」的回答比背概念值钱得多，因为它证明你真的跑过。

可以这样说 3 —— 测试报告可读性

「中文用例名在 pytest 里默认会被转义成 \uXXXX，我在 pytest.ini 里关掉了转义，让报告能直接显示中文用例名，方便定位失败。」
