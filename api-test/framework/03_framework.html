2为什么要分层

不分层也能跑，那分层的意义在哪

第一讲那个 test_posts_by_user.py，一个文件装下了所有东西：地址、数据读取、发请求、断言。它能跑，8 条全绿。

但那是因为它太简单了——只有 1 个接口、1 种请求方式。一旦接口变多，这个写法会立刻开始疼：

迟早会发生的事单文件写法下你要做什么
换测试环境（线上 → 本地） 去每个测试文件里把地址改一遍，漏一个就有一条用例在打错的地址
登录逻辑要复用 复制粘贴一遍「拼 payload + 发 POST + 取 cookie」，粘贴 3 处后改一处忘两处
加一条用例 复制一个函数、改里面的数据、改断言——数据和代码黏在一起
接口改了字段名 全项目搜字段名，逐个改

分层的根本理由就一句话：

把「变化原因不同的东西」分开放。

地址会变 → 单独一层（config.py）
接口本身会变（字段名、路径）→ 单独一层（api/）
测试数据会变（加用例、改账号）→ 单独一层（data/）
判断标准会变（期望值、断言方式）→ 单独一层（testcases/）

它们的变化原因不同，所以放不同文件。结果是：改任何一样，只需要打开一个文件。

3三个目录，三种职责

边界清楚，才知道新代码该放哪

目录结构（实际建好的）

D:\selenium\api-test\framework\
├── config.py                 ← 配置层：地址、超时。换环境只改这里
├── pytest.ini                ← pytest 的配置（testpaths / pythonpath / 中文用例名）
├── api/                      ← 请求层：怎么发请求
│   ├── __init__.py
│   └── login_api.py
├── data/                     ← 数据层：用什么数据发
│   └── login_cases.yaml
├── testcases/                ← 用例层：发了之后对不对
│   └── test_login.py
└── report.html               ← 跑完生成的报告
api/
把请求发出去，把响应原样返回。
绝不做断言、绝不判断通过失败。
data/
用例的输入数据。
新增用例只改这里，代码一个字不动。
testcases/
调 api 拿响应，然后断言。
这里是唯一出现 assert 的地方。

最容易搞混的一条边界：api/ 里不许写 assert。

为什么？因为同一个接口在不同用例里，期望值可能不一样。比如登录接口：

  • 用例「正常登录」期望 code == 0
  • 用例「密码错误」期望 code == 40102

如果 login_api.py 里写了 assert code == 0，那第二条用例根本没法写。

api 层只负责「把请求发出去」这个动作，对错留给调用它的人判断。这就是职责单一。

4逐层读代码

从最底下那层往上看

第 0 层：config.py

你 Postman 那条线学过一句话——「凡是会『变』的东西，都不能写死」。这个文件就是那句话的落地：

# 被测服务地址（就是你 JMeter 压的那个 ecommerce-demo）
BASE_URL = "http://119.45.177.154:3000"

# 单个请求的超时时间（秒）
TIMEOUT = 10

以后要测本地环境，你只改 BASE_URL 一行，全项目跟着变。这就是把「变化」集中到一个点的价值。

第 1 层：api/login_api.py

api/login_api.py（节选）

def new_session():
    """开一个会话。它会把服务器返回的 Cookie 自动存下来，
    并在后续请求里自动带回去 —— 这就是「登录状态」能保持住的原因。"""
    return requests.Session()


def login(account, password, session=None):
    """调用登录接口。返回 response 对象（原样返回，不解析、不断言）"""
    payload = {}
    if account is not None:
        payload["account"] = account
    if password is not None:
        payload["password"] = password

    http = session or requests
    return http.post(BASE_URL + LOGIN_PATH, json=payload, timeout=TIMEOUT)

三个设计点，都值得记住：

  • 参数传 None 表示「这个字段根本不传」。这样「缺少 password 字段」这种异常用例才能测——如果写成默认空字符串，那测的就是「空密码」而不是「没有密码字段」了，两个是不同的场景。
  • http = session or requests：给了会话就用会话（保持登录态），没给就单次请求。一个函数覆盖两种用法。
  • 返回原始 response，不返回 resp.json()。因为有些用例要断言状态码、有些要断言响应体，把完整的响应交出去，选择权留给上层。

第 2 层：data/login_cases.yaml

data/login_cases.yaml（节选）

test_account:
  account: "pytest_demo@example.com"
  password: "Test123456"

cases:
  - id: 正常_正确账号密码
    account: "pytest_demo@example.com"
    password: "Test123456"
    expect_status: 200
    expect_code: 0

  - id: 异常_缺少password字段
    account: "pytest_demo@example.com"
    password: ~          # 波浪号 = null = 这个字段根本不传
    expect_status: 422
    expect_code: 422

YAML 和 CSV 的一个实际差别：CSV 读出来全是字符串，所以要 int(row["expectedStatus"]) 手动转换；YAML 会自己认类型，200 就是数字 200。少一步转换、少一类坑。

另一个差别是 YAML 能写注释（# 开头）。别小看这个——真实项目里，「这条用例为什么期望 422」这种信息，写不了注释就只能靠人记。

第 3 层：testcases/test_login.py

这一层只有两个动作：调 api、断言。

testcases/test_login.py（节选）

@pytest.mark.parametrize("case", DATA["cases"], ids=lambda c: c["id"])
def test_login(case):
    resp = login(case["account"], case["password"])

    # 断言 1：HTTP 状态码
    assert resp.status_code == case["expect_status"]

    # 断言 2：响应体里的业务码
    assert resp.json()["code"] == case["expect_code"]

对比第一讲，这里有个重要进步：第一讲断言的是「返回几条」，这一讲断言的是「业务码」。

为什么业务码比「返回几条」更值得断言？

因为真实接口普遍是两层状态：HTTP 状态码 + 响应体里的业务码。{code, message, data} 就是这种结构的典型（你测的这个项目就是）。

有些接口设计得糙一点：HTTP 永远返回 200，对错全看 code。只断言 HTTP 状态码就会漏掉大量 bug——请求明明失败了，状态码还是 200，测试却绿了。

所以：两个都断言。HTTP 码确认「通信层通了」，业务码确认「业务层对了」。

5这 5 条用例是怎么设计出来的

不是随手凑 5 条，是有覆盖思路的

先看运行结果，再讲怎么来的：

实际运行结果 · 你的机器实测
用例结果
test_login[正常_正确账号密码]PASSED
test_login[异常_密码错误]PASSED
test_login[异常_缺少password字段]PASSED
test_login[异常_账号密码为空]PASSED
test_login_then_get_me（接口关联）PASSED

实测输出

collected 5 items
5 passed in 0.75s

设计思路：先划「参数的取值范围」，每个区间取一条

account + password 的组合空间：

  ┌─ 都正确、且账号存在          → 用例 1  正常_正确账号密码
  │
  ├─ 都传了，但密码不对          → 用例 2  异常_密码错误
  │
  ├─ account 传了、password 没传 → 用例 3  异常_缺少password字段
  │   （字段缺失 = 结构不对）
  │
  └─ 都传了，但都是空字符串      → 用例 4  异常_账号密码为空
      （字段存在但值为空 = 值不对）

用例 3 和用例 4 为什么算两条，而不是重复？这是最值一问：

用例 3：缺少 password 字段用例 4：password 是空字符串
请求体长什么样{"account": "x"}{"account": "", "password": ""}
问题类型结构错了——字段压根没有值错了——字段在，但内容不合法
实测返回422 提示 expected string, received undefined422 提示「请输入账号 / 请输入密码」
谁会踩到前端漏传字段（代码 bug）用户两手一摊直接点登录

注意最后两行：两条用例的 HTTP 状态码都是 422，但响应体里的提示语完全不同。

「字段没有」服务器会说 expected string, received undefined（技术语言）；「值是空的」服务器会说「请输入账号」（给人看的语言）。这是两套不同的校验分支，必须分别覆盖——只测一条，另一条永远没人验。

这就是「用例要讲究覆盖，不要凑数」的意思：区分标准不是「看起来不一样」，而是「走的是不是不同的代码分支」。

那第 5 条（接口关联）为什么单独写，不放进 YAML？

因为它不是「一次请求 + 一次断言」，而是「两次请求 + 两次断言，且第二次依赖第一次的结果」。参数化的模型是「一组数据 → 一条用例」，装不下这种有先后依赖的流程。

所以规矩是：独立的单接口用例走数据驱动；有前后依赖的流程用例单独写成函数。

6接口关联的代码版：session

你 Postman 学过「取 → 存 → 用」，这里把它写成代码

testcases/test_login.py · 第 5 条用例

def test_login_then_get_me():
    """接口关联：先登录拿到会话，再用同一个会话问「我是谁」"""
    account = DATA["test_account"]["account"]
    password = DATA["test_account"]["password"]

    session = new_session()                          # ① 开一个会话

    login_resp = login(account, password, session=session)   # ② 登录，会话记住了 Cookie
    assert login_resp.status_code == 200

    me_resp = get_me(session)                        # ③ 带着会话去问「我是谁」
    assert me_resp.status_code == 200
    assert me_resp.json()["data"] is not None        # 拿到用户信息 = 关联生效

和你 Postman 里的做法对照

步骤Postman 里你怎么做代码里怎么做
取在 Tests 里写 pm.response.json().data.token不用手动取——Session 自动把 Set-Cookie 存进 session.cookies
存pm.environment.set("token", token)同上，Session 内部存着
用请求头填 Authorization: Bearer {{token}}不用手动填——用同一个 session 发的请求会自动带上

差别来自两种不同的鉴权机制，两种都要认识：

Token 制：服务器把 token 放在响应体里给你 → 你得自己取出来、存下来、塞进请求头。Postman 的 {{token}} 就是干这个的。

Cookie 会话制：服务器通过 Set-Cookie 响应头发 Cookie → 浏览器/客户端自动存、自动带，你不用管。代码里用一个 requests.Session() 就全办了。

你测的这个项目走的是 Cookie 会话——实测带 Authorization: Bearer 是无效的，必须用会话。

关键理解：session 不是「语法糖」，它是「身份」。

换个新 session 去调 /api/auth/me，拿到的就是 data: null——因为新 session 没登录过，服务器不认识它。

所以关联的本质是：让第二个请求，带着第一个请求挣来的身份。

顺带一提：/api/auth/me 在未登录时不返回 401，而是返回 200 + data: null。这叫软失败——接口不报错，用空数据表达「你没登录」。

这种设计对前端友好（不用写异常处理），但对测试不友好：如果你只断言状态码是 200，这个接口测得再多次也发现不了「没登录」的问题。所以这里必须断言 data is not None。

7实测说了算：account 填邮箱

这一节是本讲最值钱的思维

建这个框架时撞到一个意外，值得单独讲。看两组实测：

请求实测返回
注册：{"nickname": "pytest_demo", "password": "...", "email": "..."} 200 {"code":0,"message":"注册成功"}
登录：{"account": 邮箱, "password": "..."} 200 {"code":0,"message":"登录成功","data":{"id":5,"nickname":"pytest_demo","role":"USER"}}
登录：{"account": 昵称, "password": "..."} 401 {"code":40102,"message":"账号或密码错误"}

看明白了吗：注册时用的是「昵称」，但登录时的 account 必须填「邮箱」。拿昵称去登录，服务器告诉你「账号或密码错误」——你不会想到是「格式不对」，只会以为密码错了。

这就是「账号或密码错误」这句提示的陷阱。

它把「账号不存在」「密码不对」「账号格式不对」三种情况合并成了一句模糊的话——为了安全（不让人枚举出哪些账号存在），这在真实系统里很常见。

但对测试来说，这句提示基本没有定位价值。你只能靠别的办法缩小范围。我做的是一组对照实验：

  1. 昵称登录 → 401
  2. 邮箱登录 → 200（同一个密码！）

两次只有「账号格式」这一个变量不同，结论就锁死了：问题出在账号格式，不在密码。

从这件事里提炼两条方法论

方法怎么用
控制变量 两次请求只改一个因素，才能把原因锁定到那个因素上。这跟你在这个项目里一直用的「拿应该的样子和实际的样子对比」是同一件事——只不过对比的对象从「页面」换成了「两次请求」。
接口文档不写的地方，实测说了算 字段叫 account，文档/命名不会告诉你它到底是邮箱、手机号还是昵称。测试的价值有一部分就体现在这：你是第一个把「说的和做的」对一遍的人。

顺便说一句：这个测试账号是我用注册接口建的（pytest_demo@example.com / Test123456）。

为什么不用你日常在用的账号？因为自动化用例会反复跑、会故意输错密码、密码错了就反复触发失败登录——专门开一个测试账号，才不会把你的日常账号搞出异常记录。这是测试岗的标准做法，面试可以直接讲。

9自测题（口述优先）

先自己说一遍，再展开对照

口述题
  1. 为什么要分 api / testcases / data 三层？不分层会疼在哪？
  2. api/ 层里为什么不许写 assert？举个例子说明。
  3. 用例 3（缺少 password 字段）和用例 4（password 是空字符串）为什么不能合并成一条？
  4. Postman 里做接口关联要「取 → 存 → 用」三步，代码里为什么一步都不用做？
  5. 同一个登录接口，返回 200 就代表登录成功了吗？你怎么断言才算测到位？
  6. 「账号或密码错误」这句提示，为什么它本身没有定位价值？你会怎么把范围缩小？
展开参考答案

1. 为什么分三层？

核心是把「变化原因不同的东西」分开放。
· 地址会变（换环境）→ config.py
· 接口本身会变（路径、字段名）→ api/
· 测试数据会变（加用例、改账号）→ data/
· 判断标准会变（期望值）→ testcases/
不分层的话：换环境要翻遍每个测试文件；加一条用例要复制粘贴函数再改数据；接口改个字段名要全项目搜。分层之后，改任何一样都只打开一个文件。

2. api 层为什么不许写 assert？

因为同一个接口在不同用例里期望值不同。登录接口：正常登录期望 code == 0，密码错误期望 code == 40102。如果 login_api.py 里写死了 assert code == 0，那「密码错误」这条用例根本没法写——它必然失败。
api 层只负责「把请求发出去」这一个动作，对错由调用它的人判断。这就是职责单一。

3. 用例 3 和用例 4 为什么不能合并？

因为它们走的是服务器两套不同的校验分支：
· 用例 3 请求体是 {"account": "x"}，结构不对（字段缺失）→ 服务器报 expected string, received undefined
· 用例 4 请求体是 {"account": "", "password": ""}，值不对（字段在但内容非法）→ 服务器报「请输入账号」
虽然 HTTP 码都是 422，但提示语完全不同 = 不同的代码路径。只测一条，另一条分支永远没人验。
判断两条用例是否重复，标准是「走的代码分支是否相同」，不是「看起来像不像」。

4. 代码里为什么不用「取 → 存 → 用」？

因为鉴权机制不同。
· Token 制：token 在响应体里，得自己取、存、塞进请求头 —— 这就是 Postman 的 {{token}}。
· Cookie 会话制：服务器用 Set-Cookie 响应头发 Cookie，客户端自动存、自动带。requests.Session() 把这三步全办了，所以代码里看着「什么都没做」。
你测的这个项目是 Cookie 会话制（实测带 Bearer 无效）。所以不是代码省略了步骤，是机制本身就不需要手工传递。

5. 返回 200 就代表登录成功吗？

不代表。真实接口普遍有两层状态：HTTP 状态码 + 响应体里的业务码。
更要注意的是「软失败」设计：/api/auth/me 未登录时返回的是 200 + data: null，不是 401。这种接口只断言状态码永远测不出问题。
所以要两个都断言：status_code == 200 且 code == 0；涉及数据的还要断言 data 不为空。

6. 「账号或密码错误」为什么没有定位价值？

因为它把「账号不存在」「密码不对」「账号格式不对」三种情况合并成了一句模糊提示——这是有意为之，为了防止别人枚举出系统里有哪些账号。
但对测试来说，这句话不能帮你缩小范围。做法是控制变量：
① 用昵称登录 → 401
② 用邮箱登录（密码一模一样）→ 200
两次只改了「账号格式」一个变量，结论就锁死了：问题在账号格式，不在密码。

10面试怎么讲这一块

你亲手搭的，讲起来比背答案有说服力

可能被问到你可以这样答
你的接口自动化框架怎么分层的？ 三层：api/ 封装请求、testcases/ 写用例和断言、data/ 放 YAML 测试数据，另外把环境地址抽到 config.py。分层的依据是「变化原因不同」——换环境改 config，加用例改 data，接口字段变了改 api，互相不牵连。
为什么 api 层不写断言？ 同一个接口在不同用例里期望值不一样（正常登录期望 code 0，密码错误期望 code 40102），断言写在 api 层就没法复用了。api 层只负责发请求并原样返回响应。
接口返回值你怎么断言？ 两层都断：HTTP 状态码 + 响应体业务码。特别要提软失败的情况——有些接口未登录也返回 200，只是 data 为 null，只断状态码会漏问题。
怎么测有依赖的接口（比如先登录）？ 用 requests.Session() 保持会话。登录成功后 Session 自动持有 Cookie，后续请求用同一个 Session 发就带上了身份。Token 制的接口则要手动取 token 放进请求头。
测试账号怎么管？ 专门的测试账号，不用真人账号。因为自动化会反复跑、故意输错密码，会污染真人账号的失败登录记录。账号数据放在 data 里，不硬编码在代码里。
测试数据为什么用 YAML？ YAML 能写注释、能表达层级、可读性好，真实项目更常见。扁平的简单数据用 CSV 也完全可以，选型看数据形状。

你现在手里握着两个别人背不出来的细节，面试时说出来会很不一样：

① 「我为了给登录接口做自动化，专门注册了一个测试账号，没有用真人账号」
② 「我发现登录字段叫 account，但实际要填邮箱不是昵称——拿昵称登会返回 40102 账号或密码错误，这句提示没有区分度，我是用控制变量法试出来的」

第二句尤其值钱。它同时证明了你会用控制变量、你会怀疑模糊错误信息、你做事是实测驱动而不是猜。这种细节，只有真动手的人讲得出来。
