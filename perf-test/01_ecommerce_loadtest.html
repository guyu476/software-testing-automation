0这次压的是什么

先明确靶子、规模和"为什么这么设计"。

测试环境
项目ecommerce-demo（D:\ecommerce-demo）
技术栈Next.js 16.3.4（App Router / Turbopack）+ Prisma 6 + MySQL 8
运行模式dev 模式（next dev -p 3000）← 后面第 5 节专门讲这个的影响
靶子地址http://127.0.0.1:3000
数据12 个商品、6 个分类、2 家店、3 个用户（seed 数据）
压测工具Apache JMeter 5.6.3（JDK 21），命令行模式
并发规模20 个并发用户 × 5 轮，三个接口各跑 100 次，合计 300 个请求

为什么选这三个接口

它们代表三种完全不同的负载类型，放一起压才能看出区别：

  • GET /api/health —— 不查数据库，只返回一段写死的 JSON。它的耗时几乎等于"框架本身的转发开销"，是天然的基线。
  • GET /api/products?page=1&pageSize=10 —— 典型查库接口。代码里是一次 $transaction([count, findMany])，同时算总数和取列表。
  • GET / —— 首页 SSR，最重的用户入口。整页服务端渲染，返回 131 KB HTML。

为什么压自己的项目，而不是随便找个网站？两个原因。一是压出问题你能改——看到哪个接口慢，可以直接去翻代码；二是想加多少并发都行，本地服务压垮了也只是你自己的笔记本重启一下，不涉及任何第三方的生产系统。

1结果：三个接口横向对比

这是 JMeter 聚合报告里那几行数据的原文。

聚合报告（按接口分行）

/api/health100620 ms15 ms1484 ms0.00%
/api/products100601 ms20 ms1524 ms0.00%
/ 首页 SSR1001399 ms178 ms2419 ms0.00%

三个数字要一起读：

  • 300 个请求、16 秒跑完 → 吞吐量 18.7 req/s。这就是「每秒能处理多少请求」，面试里说的 TPS / QPS 就是这个位置。
  • 错误率 0% → 20 并发没有打崩你的服务。而且这个 0% 是验过内容的：每个接口都挂了断言（health 要含 "status":"up"，商品列表要含 "total"，首页要含 <!DOCTYPE html>），不是"请求发出去了没报错"就算过。
  • 同一个"20 并发"，三个接口的平均响应差了 2.3 倍（601 → 1399 ms）。往下看为什么。

2结论一：并发不是线性关系

这是性能测试里最反直觉、也最能体现你懂行的一条。

单发一个请求时，/api/health 只要 38 毫秒。加到 20 并发之后，它变成 620 毫秒——慢了 16 倍。

同一个接口，不同压力下的表现
场景平均响应时间
单请求（1 个用户，无并发）38 ms
20 个并发用户620 ms

为什么不是"20 倍压力 = 20 倍速度"？因为服务端不是"20 个人各干各的"。Node.js 处理你的业务代码是单线程的：20 个请求同时到达，它们排队一个个被执行。第 20 个请求要等前面 19 个都处理完才开始——等待时间自然叠上去。

这条经验的价值：只看"单请求很快"是不能下结论的。一个接口单发 38ms，你可能觉得"性能很好"；但真实场景是几百个人同时刷，那时它是 620ms。性能测试的全部意义就在于把并发加上去，看真实用户量下的表现。

面试被问到"你怎么判断一个接口有没有性能问题"，这就是标准回答路径：先测单请求基线 → 再加并发 → 看响应时间和错误率怎么变。

3结论二：拆开看才知道谁慢

这里直接用到你上一讲学的 Connect Time / Latency / Load time 三个字段。

首页平均要 1399 毫秒，是 health 的 2.3 倍。但"1399 毫秒"这一个数字说明不了任何问题——是网络慢？是数据库慢？还是渲染慢？必须拆开。

三个接口的耗时构成（平均值）
接口Connect TimeLatency
（到首字节）		Elapsed
（到末字节）		传输耗时
= Elapsed - Latency
/api/health0.4 ms620 ms620 ms0 ms
/api/products0.0 ms601 ms601 ms0 ms
/ 首页 SSR0.0 ms1254 ms1399 ms145 ms

读出三件事：

  1. 首页的大头在服务端。1254 ms 的 Latency 意味着"服务器想了 1.25 秒才吐出第一个字节"——这段时间花在 React 服务端渲染 + 查数据库上。而最后那 145 ms 才是把 131 KB HTML 传给你的时间。
  2. 两个 JSON 接口的传输耗时几乎是 0（响应体才 5 KB 上下，本地网络瞬间传完）。所以它们的耗时 100% 是服务端处理。
  3. 如果只盯着"总响应时间 1399ms"，你可能会去优化网络、加 CDN、开压缩——全都优化错了地方。真正该看的是那 1254 ms 的服务端渲染。

这就是那三个字段的实战价值：它把"一次请求"切成「建连接 / 服务器思考 / 数据传输」三段。哪段长，问题就出在哪。没有这个拆分，你只有一坨总数，根本不知道从哪下手。

4结论三：Connect Time 是 0 才对

这条专门讲一个容易误判的地方。

看上面那张表：三个接口的平均 Connect Time 分别是 0.4 ms / 0.0 ms / 0.0 ms，几乎是零。新人第一反应往往是"这个字段是不是没采集到"或"数据坏了"。

不是坏了，这是正常且正确的。看逐条样本就清楚了：

/api/health 的前几条原始样本
Connect=16   Latency=40    Elapsed=44
Connect=1    Latency=15    Elapsed=15
Connect=1    Latency=209   Elapsed=209
Connect=0    Latency=114   Elapsed=114
Connect=0    Latency=30    Elapsed=30
Connect=0    Latency=371   Elapsed=371

只有第一条有 Connect Time（16 ms），后面全是 0。原因是 JMeter 默认开启 keep-alive（连接复用）：同一个线程第一次请求时建立 TCP 连接（所以有 16ms），之后这个连接一直留着重复使用，不再需要重新建连——所以 Connect Time 就是 0。

反过来的场景要记住：如果你压的是外网站点、或者每个请求都需要新建连接，Connect Time 就会明显起来。上一讲压 httpbingo.org 时它平均是 730 ms——因为那是真实的公网 TLS 握手。

所以判断标准是：Connect Time 为 0 = 连接被复用了，这是好事；突然变大 = 连接没有被复用，或者网络出问题了。这两种情况都是有意义的信号，需要能分辨。

5重要：dev 模式的 51 倍陷阱

这一节比前面所有数字都重要，它决定你会不会把时间花在错的地方。

压测开始前，我先单独访问了每个路由两遍。结果如下：

同一个路由，连续访问两次
路由第 1 次访问第 2 次访问慢了多少倍
/api/health2112 ms8 ms264×
/api/products122 ms32 ms3.8×
/ 首页8757 ms171 ms51×

首页第一次要 8.7 秒，第二次只要 171 毫秒。差的这 8.5 秒完全没有花在你的代码上，而是 Turbopack 在编译这个路由。

如果不预热就直接压，你会得到一份完全错误的报告。第一个请求的 8.7 秒会把平均值拉高，然后你会得出"我的首页要好几秒"的结论，接着去优化数据库查询、优化 React 组件、加缓存——而这些都是白费力气，因为真正的瓶颈是开发服务器的编译器。

所以本次压测的流程里专门加了一步"预热"：先手动把每个路由各访问一遍、等编译完成，再开始正式压测。上面那张对比表就是预热的依据。

这不只是 dev 模式的问题

"第一次慢、后面快"是所有服务端系统的通用现象，专业叫法是冷启动（cold start）。生产环境同样有，只是原因不同：

  • JIT 编译器还没把热点代码编译成机器码（Java / JVM 系统尤其明显）
  • 数据库连接池还没建立连接，第一个查询要现连
  • 各种缓存（页面缓存、查询缓存、DNS 缓存）全是空的

所以工业界的做法是：压测报告里要注明"是否含预热"，或者干脆丢掉最初的一批样本。你以后看别人的性能报告，第一件事就是确认这一条。

关于本次数据的适用范围，必须说清楚：上面所有数字（620ms / 601ms / 1399ms）都是 dev 模式下的。dev 模式为了快速热更新，关掉了大量生产优化，React 跑的是开发版本，页面体积也更大。真实生产环境会比这个快得多。

所以这份数据的作用是学会方法、看清趋势、找出相对最慢的接口，不能当成"我这个项目性能就是 1399ms"的对外基线。要一个能写进汇报的基线，得用 next build && next start 的生产模式重新压一次（见第 7 节）。

  4. 聚合报告里 Connect Time 平均 0 毫秒，这是数据错了吗？如果它突然变成 500 毫秒，你会怎么判断？
  5. 如果你要给这个项目定一个能对外汇报的性能基线，现在这份数据能用吗？为什么？
想好了再点开对答案
1. 为什么必须先预热？

因为服务端有"冷启动"开销——dev 模式下是编译器要在首次访问时编译路由（首页 8.7 秒 vs 171 毫秒，差 51 倍），生产环境是 JIT 编译、连接池建立、缓存未命中等。不预热的话，你测到的是启动开销而不是服务真实性能，会得出"我的接口很慢"的错误结论，然后去优化根本不存在的瓶颈。做法：正式压测前把每个目标路由各访问一两遍，等它稳定下来。

2. 38ms → 620ms 说明什么？

说明服务端处理能力有限，请求在排队。Node.js 执行业务代码是单线程的，20 个并发请求要依次被处理，后来的请求要等前面的完成，等待时间会累积。所以并发数增加时响应时间不是线性增长，而是加速恶化。这条经验的价值在于：只看单请求快不能说明性能好，必须把并发加上去测。

3. 1399ms 里服务器慢还是传输慢？

看 Latency（到第一个字节的时间）和 Elapsed（到最后一个字节的时间）的差。首页是 Latency 1254ms、Elapsed 1399ms，差值 145ms 是传输 131KB HTML 的时间，剩下 1254ms 全是服务器在想——即 React 服务端渲染加数据库查询。所以瓶颈在服务端渲染，不是网络。

4. Connect Time 是 0，正常吗？

正常。JMeter 默认开启 keep-alive 连接复用：每个线程第一次请求建立 TCP 连接（样本里能看到第一条是 16ms），之后这个连接被反复使用，不需要重新建连，所以 Connect Time 记为 0。如果它突然变成几百毫秒，说明连接没有被复用（比如服务端主动断开、或换了目标），那才是异常信号，要顺着查。

5. 这份数据能当对外基线吗？

不能。因为是 dev 模式的数字——dev 为了热更新关闭了大量生产优化，React 跑开发版本，页面体积更大。它的用途是学方法、看趋势、横向比较哪个接口最慢。要用生产模式（next build 然后 next start）重新压一遍，得到的才是能写进报告的基线。

7下一步能做什么

三个方向，按价值排序。

① 阶梯加压，找"拐点"

这次只试了 20 并发一个点。真正的性能测试要做阶梯加压：10 → 20 → 50 → 100 并发各压一轮，观察响应时间和错误率在哪一档开始明显变坏。那个开始变坏的并发数，就是这套服务在当前配置下的容量拐点——这才是性能测试最值钱的产出。

② 出一份生产模式的基线

先 npm run build，再用 npm start 启动，然后重压一次。这次的数字会和 dev 模式差很多，那个才是真实性能。有了这个，你才敢说"我这个项目首页在 N 并发下平均 X 毫秒"。

③ 压带业务逻辑的接口

这次压的三个都是读接口（GET），不会改数据。往下可以压真正重的写链路——比如下单 POST /api/orders，它涉及事务、条件扣库存、幂等键抢占。但要注意两点：需要登录态（JMeter 要加 Cookie 管理器），而且会真的写数据，压完得清理。

现在你手上有什么：一套能反复使用的压测流程（启动项目 → 预热 → 压 → 看报告 → 关掉），三个已经写好的测试计划，以及这份记录了方法和坑的报告。下次想压，双击两个文件就行，具体见本文件所在目录的 启动电商项目.bat 和 压测3-电商项目.bat。
