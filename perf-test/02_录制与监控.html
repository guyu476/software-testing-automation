0先想清楚：录制到底给你什么

不想清楚这一点，录下来的东西基本都是废的

录制的原理一句话：JMeter 把自己变成一个代理服务器，浏览器的每个请求都得先经过它，它顺手抄一份下来。

所以录制能给你的只有一件事 —— 请求骨架：

  • URL 长什么样（路径、查询参数）
  • 用什么方法（GET / POST）
  • 请求头带了什么（Cookie、Content-Type、User-Agent）
  • POST 的请求体长什么样

它给不了你的是：

  • 判断对错的能力 —— 录下来的请求没有断言，JMeter 默认只看 HTTP 状态码
  • 可变的数据 —— 录的时候参数是什么，跑的时候还是什么
  • 干净的清单 —— 浏览器发什么它就抄什么，图片、JS、统计脚本一个不落

一句话总结：录制是「省手抄」，不是「省思考」。该录的场景是「探索一个不熟悉的系统、快速拿到接口清单」；该手写的场景是「压测、要参数化、有接口文档」。你现在做的是压测 —— 所以录制的价值主要在第一轮摸底，最终还是要自己收拾干净。

1录制器与证书：什么时候需要

这一个元件是自带的，那张证书是有条件的

元件本身：不用装任何插件

HTTP(S) 测试脚本记录器 是 JMeter 自带元件，跟「线程组」「HTTP 请求」是同一个级别的东西。装 JMeter 的时候它就在了。

这点跟 Fiddler 不一样：Fiddler 要看某种报文格式得去找查看器扩展，JMeter 的录制器开箱即用。

证书：只有录 https 才需要

录制的目标协议 vs 要不要装证书
目标地址要装证书吗原因
http:// 开头不需要明文进出，代理直接可读
https:// 开头需要加密内容，代理必须先「冒充」目标站点，浏览器才肯解密交出

「冒充」这件事靠的是：录制器当场生成一张根证书，再把这张根证书装进系统的「受信任的根证书颁发机构」。装了之后，浏览器才承认录制器临时签发的站点证书是合法的。

这张证书不用去外面下。点录制器面板上 State 那一行的绿色「启动」按钮时，JMeter 会弹一个提示框，同时把证书写到你 JMeter 的 bin 目录下。文件名和用途：

点「启动」后 bin 目录多出的文件
文件大小参考是什么
ApacheJMeterTemporaryRootCA.crt~1.6 KB要装到系统里的就是它
ApacheJMeterTemporaryRootCA.usr~1.6 KB同一张证书的副本（JMeter 内部用）
proxyserver.jks~8 KBJMeter 自己的密钥库，别删别动

弹窗里三条容易漏掉的信息（原文要点）：

1. 证书有效期只有 7 天。过期了要重新生成、重新装。
2. 原文 "if the created one is newer than the last one you installed, ensure you remove the old one and install the new one" —— 意思是这张证书是可以反复生成的，如果你后来生成的比之前装的更新，就要先把旧的卸掉再装新的，否则系统里会堆一堆同名证书，以后排障很痛苦。
3. 弹窗会给你三条核对信息：CN= 里带 OU=Username: 你的用户名、一串 Fingerprint(SHA1)、以及 Created 时间。装之前核对这三项，确认装的是自己这台机器生成的证书。

证书名字里那句全大写的 INSTALL ONLY IF IT S YOURS 不是客套话。装了别人机器生成的根证书，等于把那台机器能解密的所有流量都交出去 —— 你装之前会看到它。

顺手记住：端口 8888 是共用的

JMeter 录制器默认监听 8888，这跟 Fiddler 是同一个端口。所以 这两个工具不能同时开录制，谁先启动谁占住，后开的那个会因为端口被占用起不来（或者悄悄失败）。

2为什么浏览器录不到本地项目

录本地是经典坑，不是你的操作问题

假设你要录 http://127.0.0.1:3000/。录制器启动了、端口也配了、浏览器代理也设了 —— 结果录制器里一条都不多。

原因不在 JMeter，在「代理绕过列表」。

两层绕过，都得注意

localhost / 127.0.0.1 的两层特殊性
层面发生了什么
Windows 系统代理设置「不对以下列表中的地址使用代理服务器」这一栏，默认就含 localhost;127.0.0.1
浏览器自己的代理逻辑浏览器普遍硬编码：指向本机的请求不走代理

结果是请求绕过 8888 直接发出去了，录制器自然看不到。

绕开它：用 curl 强制走代理

要验证「录制器到底能不能记下东西」，最省事的办法是用 curl。curl 不看系统的绕过列表，你用 -x 指定了它就一定走。

在命令行窗口里执行（本机 PATH 里没有 curl，所以写全路径）：

"C:\Windows\System32\curl.exe" -x http://127.0.0.1:8888 http://127.0.0.1:3000/api/products

执行完回到 JMeter，看左边元件树 —— 应该多出一条 /api/products 记录。

为什么推荐先用这一步？因为它把三个变量一次性排除了：不用装证书、不用改浏览器代理、不用跟绕过列表较劲。你要先亲眼看到「经过 8888 的请求会被记下来」这一件事，才轮到解决「怎么让浏览器也走 8888」。

如果这时一条都不多，那问题在录制器本身（没启动成功 / 端口没监听），跟浏览器一点关系都没有。

换一个不是 localhost 的靶子，问题自然消失

如果靶子是服务器的 IP 或域名（比如 http://119.45.177.154:3000/），那它既不在绕过列表里、也不是「指向本机」，代理设置直接生效，这个坑整个不存在。

结论：想练浏览器录制，用远程地址最省事；非要在本地录，就得显式调整绕过列表，或者干脆放弃浏览器、改用 curl / Postman 直接发请求过代理。

3录到了什么：一次真实的录制复盘

这是真事，不是假设的场景

下面这份数据来自一次真实录制：靶子是本地某电商项目（Next.js 服务端渲染），用真实浏览器走了一遍商品详情页。

浏览器发出的请求 vs 其中的业务接口
访问的页面浏览器发出的请求数其中 /api/* 业务接口传输量
首页 /3401397 KB
商品详情 /products/12701502 KB

首页那 34 条的构成：17 条前端框架的 JS/CSS 分包 + 16 条商品图片 + 1 条 HTML 文档。

一条业务接口都没有。如果你直接拿这份录下来的东西去做压测，压的是「JS 和图片的分发」，跟你的业务逻辑没关系 —— 压出来的漂亮数字毫无意义。

为什么是 0 条：SSR 与 CSR 的区别

这是本讲最值得记住的一个概念。

服务端渲染 vs 客户端渲染：浏览器会调接口吗
渲染方式数据从哪来浏览器打开页面时会调 /api/* 吗
服务端渲染（SSR）服务器提前把数据取好，直接「烙」进 HTML不会
客户端渲染（CSR）浏览器加载后自己用 fetch 去要数据会

所以录制器能不能录到接口，取决于你访问的是哪种页面：

  • SSR 页面（首页、商品详情、店铺页）→ 录到的是 HTML + 一堆静态资源
  • CSR 页面（登录、购物车、订单、收藏）→ 能录到 /api/*，但通常需要登录态

怎么自己判断一个页面是哪种？不用看代码，看现象：打开页面，如果 URL 一进去内容就全了（没有「加载中」的一瞬间），多半是 SSR；如果先进去再「刷一下」内容才出来，那就是 CSR —— 这一下就是它在发接口请求。

4拿到脚本后的四步加工

录制只完成了一半，这四步才是测试的活

假设你已经录到一份能跑的脚本。下面是必须做的四步，顺序别乱。

第一步：过滤静态资源

录制器面板里有一个 「URL 模式」相关的输入区（在面板中下部，标签含 URL Patterns to Exclude）—— 在这里填正则，把不想录的挡在外面。

常见的几类该排除的：

图片  \.(png|jpg|jpeg|gif|svg|webp|ico)
样式  \.css
脚本  \.js
字体  \.(woff2?|ttf|eot)

已经录进来的怎么办？不用一条条删。在元件树上按住 Ctrl 多选、或按住 Shift 选一片，然后右键 → 删除。或者右键 → 禁用（禁用比删除安全，出问题还能恢复）。

第二步：参数化

录下来的参数是字面量。比如录的时候商品 ID 是 2，跑起来 100 次全都是 2 —— 这就不叫压力测试了，叫「对同一个商品查 100 次」。

参数化的最小做法：把死值换成变量，再用 CSV 数据文件设置 喂不同的值。这属于第三讲的内容，这里先知道「必须做」就行。

一个真实的例子：录制某项目的「加入购物车」请求，请求体长这样：
{"productId": 2, "quantity": 1}
这两个数字都是录下来的那一刻的值。productId 必须参数化，否则你永远在压同一个商品。

第三步：关联

上一个请求返回的东西，被下一个请求用上 —— 这个传递动作叫关联。

典型场景：登录接口返回一个 token，后续所有接口都要在请求头里带这个 token。录的时候 token 是当时那一个，你直接跑，token 早就失效了 → 全部请求返回 401。

做法是「三个动作」：取出来（后置处理器）→ 存成变量 → 用的时候引用变量。

第四步：加断言

这一步最容易被跳过，也最致命。

JMeter 默认只检查 HTTP 状态码。服务器返回一个内容全错的页面，只要状态码是 200，JMeter 就判定「成功」。
于是你的聚合报告上显示 Error 0% —— 这个数字是假的，它只说明「服务器还活着并且回了包」，什么都没证明。

加断言的路径（右键元件）：

右键「HTTP 请求」
  → 添加
    → 断言
      → 响应断言

常用的两种断言字段：

响应断言的两个关键字段
要测的字段用途测试模式填什么
响应文本检查响应体里有没有某个关键词比如 "code":0
响应代码检查状态码比如 200

填「响应文本」的判断串时，就填你在响应里能看到的原样字符，不要加正则里的 \b、.* 这类符号 —— 那个输入框默认按「包含/匹配」处理文本，不按正则处理。多打两个字符，断言就会永远失败，而你会以为是服务器的问题。

5监控：监听器怎么选、挂在哪

这就是「仪表盘」，是 JMeter 自带的元件

性能测试里说的「监控」，在 JMeter 的语境下就是监听器：它负责收集取样结果、并把结果呈现出来。跟「线程组」「断言」是同一类元件。

先搞清楚挂在哪

元件树是有层级的，监听器挂的位置决定它能收到哪些请求：

测试计划
└── 线程组
    ├── HTTP 请求 1
    ├── HTTP 请求 2
    └── [监听器挂这层]        ← 最常用：能看到这个线程组的所有请求
监听器的三种挂法
挂在哪效果
线程组下面（与请求平级）只管这个线程组 —— 最常用，层次清楚
测试计划根下管所有线程组 —— 多个线程组要汇总时用
某个请求下面只管这一个请求 —— 想单独盯住某个接口时用

常用的几个，以及该什么时候用

监听器选型
监听器看什么什么时候用开销
聚合报告汇总数字表格压测的主力，几乎总开着很小
查看结果树每条请求的请求/响应全文脚本还没跑通、断言失败了要排查很大
响应时间图响应时间随时间的曲线找「什么时候开始变慢」的拐点中
聚合图 / 汇总报告与聚合报告类似的不同呈现可选，别重复加小

「查看结果树」是内存杀手。它会把每一个请求和每一个响应的完整内容都留在内存里。跑几十个请求无所谓，一旦上到几万请求，JMeter 自己会先撑不住 —— 而「JMeter 卡住」和「服务器变慢」在结果里长得很像，你根本分不清。

做法：压测前右键它 → 禁用。它是调试工具，不是压测工具。

6聚合报告：每个字段怎么读

这张表是性能测试的核心，读不懂它等于白压

聚合报告是一张多列表格，每行一个请求标签，最后一行是总体。列的含义：

聚合报告字段速查
列名含义怎么用
Label取样器的名字建议自己改成有意义的名字，否则报告没法读
# Samples这个标签发了多少个请求校验规模对不对
Average平均响应时间（ms）最直观，但容易被极端值拉偏
Median中位数（50% 的请求快于它）比平均值更抗干扰
90% Line90% 的请求快于这个值关键指标：平均值好看但 90% 线难看，说明有相当一部分用户很慢
95% / 99% Line同上，不同分位高要求场景看这个
Min / Max最快 / 最慢看波动幅度
Error %失败比例不加断言时这个数字没有意义
Throughput吞吐量，右侧标注单位这就是 TPS/RPS，压测的核心产出
Received KB/sec每秒收到的数据量带宽是不是瓶颈

两个最实用的判读习惯：

1. 先看 Error % 再说别的。错误率高的时候，所有的响应时间数字都没意义（快速失败也是一种「快」）。
2. Throughput 那一列有三个同名项，是同一指标按「每秒 / 每分钟 / 每小时」三种口径给出的，读的时候确认单位，别当成三个指标。

平均值 vs 90% Line：一个必须讲清的例子

平均值 200ms听起来很好
90% Line 1500ms但有 10% 的用户等了 1.5 秒以上 —— 换个说法：100 个人里有 10 个人觉得很卡

面试点：「为什么不能只看平均响应时间？」—— 答「平均值会被少数极端值拉偏，也掩盖了长尾；要看 90%/95% 分位，才能知道差的那部分用户体验有多差」。

7命令行跑压测 + 生成 HTML 报告

官方要求的做法，也是生成那份报告的唯一途径

为什么必须用命令行

JMeter 官方文档原话：

GUI mode should only be used for creating the test script, CLI mode (NON GUI) must be used for load testing.

道理很实在：界面本身开着图形面板、实时画图，它自己要吃掉一部分 CPU 和内存。压测的时候，你分不清响应时间变长是因为服务器扛不住了，还是因为你自己的 JMeter 界面卡住了。测量工具不能干扰被测对象。

所以分工是：GUI 只用来搭脚本和调试，真压的时候用命令行。

四个参数

"D:\selenium\jmeter\bin\jmeter.bat" -n -t "计划文件.jmx" -l "结果.jtl" -e -o "报告目录"
命令行参数
参数含义
-n非 GUI 模式（Non-GUI），不弹窗口
-t指定测试计划文件（.jmx）
-l结果写到这个文件（.jtl）。文件必须不存在，已存在会报错，这是防覆盖
-e跑完后生成 HTML 报告
-o报告输出目录。目录必须不存在或为空，否则报错

为什么「文件必须不存在」这条要单独记？因为重复跑的时候最容易踩：第二次跑你会看到类似「文件已存在」的错误而不知道发生了什么。做法是每次生成带时间戳的新文件名，比如 result_015307.jtl。

屏幕上那个 summary 行

命令行跑的时候，屏幕上会不断刷新这样一行：

summary =    100 in 00:00:08 =   12.0/s  Avg:   367  Min:    13  Max:   702  Err:     0 (0.00%)

逐个读：

  • 100 —— 一共发了 100 个请求
  • in 00:00:08 —— 用了 8 秒
  • 12.0/s —— 吞吐量，每秒 12 个请求（就是 TPS）
  • Avg: 367 —— 平均响应时间 367 毫秒
  • Min: 13 / Max: 702 —— 最快 13 毫秒、最慢 702 毫秒
  • Err: 0 (0.00%) —— 失败 0 个，错误率 0%

HTML 报告长什么样

加 -e -o 之后，目标目录里会生成一个完整的小网站，主文件是 index.html。直接双击用浏览器打开，左侧是菜单：

  • Dashboard —— 首页概览（测试信息 + 几条核心曲线）
  • Charts → Over Time —— 响应时间随时间的曲线、活跃线程数、吞吐量曲线
  • Charts → Throughput —— 吞吐量
  • Charts → Response Times —— 响应时间分布（含分位数）

这套报告的价值在于「能发给别人」。它是一堆静态文件，打包发给同事、或者挂到内部服务器上，对方直接点开就能看 —— 不需要装 JMeter，也不需要懂怎么操作。这就是性能测试的交付物。

展开参考答案
第 1 题

它把自己变成一个代理服务器（默认 8888），所有请求都得先经过它，它顺手把请求抄下来生成取样器。

第 2 题

因为内容是加密的。录制器要「冒充」目标站点给浏览器签发一张临时证书，浏览器才肯按协议把内容交给它。而浏览器只信任系统根证书库里的颁发者，所以要把录制器生成的根证书装进「受信任的根证书颁发机构」，这张「冒充」才成立。

第 3 题

请求绕过了代理。Windows 系统代理的「绕过列表」默认包含 localhost / 127.0.0.1，浏览器也普遍对本机地址不走代理。请求直接发出去了，录制器看不到。跟证书无关。

第 4 题

那多半是服务端渲染（SSR）的页面。数据是服务器提前取好、直接写进 HTML 的，浏览器打开页面时不需要再调接口，所以只能录到 HTML 文档和静态资源。要录到接口得去客户端渲染（CSR）的页面，比如登录、购物车。

第 5 题

不一定，甚至经常是假的。JMeter 默认只检查 HTTP 状态码，不加断言的话，服务器返回内容全错的页面但状态码 200，也会被判成功。必须先加断言，错误率才有参考价值。

第 6 题

GUI 本身的图形面板、实时图表会消耗 CPU 和内存，会污染测量结果 —— 你分不清变慢是服务器的问题还是自己工具的问题。测量工具不能干扰被测对象。GUI 只用于搭脚本和调试。

第 7 题

平均值会被少数极端值拉偏、也会掩盖长尾。90% Line 表示「90% 的请求快于这个值」，能暴露那部分慢的请求。两者差异很大（比如 Avg 200ms 但 90% Line 1500ms）说明有相当比例的用户体验很差，只看平均值会漏掉这个问题。

第 8 题

会报错退出。JMeter 故意不允许覆盖，防止你把上次的结果冲掉。做法是每次用带时间戳的新文件名，或者先把旧文件移走。
