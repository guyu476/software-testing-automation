接口测试 · 断言脚本详解

Scripts → After response：断言怎么写

B 站教程里那个 Tests 标签，在你的版本里叫 Scripts，点开后左边那一列里的 After response。这份文件专门讲这一页：怎么用、能断言什么、写错了长什么样。

内容全部基于你自己的 Postman 版本界面写的，每一步都指明点哪里。练习对象仍是公开 API JSONPlaceholder，不用注册。

1这一页是什么、什么时候跑

先搞清楚执行时机，才知道为什么断言写在这里

位置：请求区的标签行 → Scripts → 左边一列里的 After response。

不同版本的叫法不一样，别被教程绕晕

同一个功能，Postman 前后改过三次名字：

  • Tests —— 老版本，B 站教程大多是这种
  • Post-response —— 中间版本
  • After response —— 你的版本，认这个

对应的，请求前脚本那一页也改过名：Pre-request Script → Before request。

找的时候认特征，别认位置：Scripts 点开后，左边那一列就是这两个子页。带 response 或 test 字样的那个，就是写断言的地方。

它是什么：一段 JavaScript。每次你点 Send，响应回来之后，Postman 会自动把这段代码跑一遍。

① 点 Send请求发出去
② 服务器返回响应到手
③ 跑脚本After response 执行
④ 出结果Test Results 打勾或打叉

为什么叫 After response 而不是 Tests？

因为它是按执行时机命名的，不是按功能。Before request 是请求发出之前跑（用来准备数据），After response 是响应回来之后跑（用来验证结果）。

只有响应到手了，你才拿得到状态码、响应时间、响应体 —— 所以断言只能写在 After response 里。

这一页上有三样东西：

位置是什么你怎么用
中间大代码框你写脚本的地方手打，或从右边点进来
右侧 Snippets 列表现成的代码片段点一下自动插到光标处
请求区左下角 Console脚本的调试窗口看 console.log 的输出

另外，请求区最底下有一行灰字 + Add post-response tests —— 那是快捷入口，点一下直接跳到这一页并起个头。视频里那句 Fix status code assertion 提示，现在改叫这个了。

一个必须建立的认识：断言不是"再发一次请求"，它只是在已经拿到的响应上做判断。所以改断言之后必须重新 Send，它才会重新跑。

2先跑通第一条断言

五分钟，从 0 到看到绿勾

按顺序做：

  1. 地址栏填 https://jsonplaceholder.typicode.com/posts/1，方法选 GET
  2. 点标签行里的 Scripts
  3. 点左边那一列里的 After response
  4. 把下面这段贴进代码框
// 最简单的断言：只验证状态码
pm.test("状态码是 200", function () {
    pm.response.to.have.status(200);
});

5. 按 Ctrl+S 保存（不保存也能跑，但下次打开就没了）

6. 点 Send

7. 看响应区那一排，多出 Test Results，显示 1/1

看到 1/1 就算跑通了。展开 Test Results，能看到那条断言的名字和绿勾。

关键一步：故意让它失败

把 200 改成 201，再 Send：

pm.test("状态码是 200", function () {
    pm.response.to.have.status(201);   // 故意写错
});

你会看到 Test Results 变成 0/1，展开后有红叉，还有一行英文告诉你错在哪：

AssertionError: expected response to have status code 201 but got 200

这一步不要跳过。

一个从没见它变红的断言，你没法确定它是真的在工作，还是它根本没跑。

面试里也会问："你怎么验证你的断言是有效的？" —— 标准答案就是故意构造一个失败的输入，看它会不会红。

看完记得把 201 改回 200。

3pm.test 的结构

理解了这个结构，后面所有断言都是同一个模子

pm.test("测试的名字（会显示在报告里）", function () {
    // 这里写真正的判断
});
部分是什么要注意什么
pm.testPostman 提供的函数，用来"登记一条测试"所有断言都必须包在它里面
"测试的名字"字符串，给人看的会出现在 Test Results 和批量报告里，要写清"在验什么"
function () { }真正做判断的地方里面才是 pm.expect(...) 这类断言

最容易搞混的一点：pm.test 本身不判断任何东西。它只是"开一个盒子"，判断是盒子里面的代码做的。

所以如果你把代码写成了下面这样，什么都不会发生 —— 因为它没有装进盒子里：

pm.response.to.have.status(200);   // 没有 pm.test 包着，Test Results 里看不到

为什么每条断言要单独包一个 pm.test？

假设你写了 5 条检查，全塞进一个 pm.test 里，和分成 5 个，差别很大：

坏例：全塞一个好例：分成 5 个
pm.test("检查", function () {
    pm.expect(b.id).to.eql(1);
    pm.expect(b.userId).to.eql(1);
    pm.expect(b.title).to.be.a("string");
    pm.expect(b.body).to.be.a("string");
    pm.response.to.have.status(200);
});
 
pm.test("状态码是 200", function () {
    pm.response.to.have.status(200);
});
pm.test("id 是 1", function () {
    pm.expect(b.id).to.eql(1);
});
// ……其余同理
第 1 条一挂，后面 4 条根本不跑。报告只显示"检查失败"，你只知道"有问题"，不知道是哪一个字段错。 5 条全部跑完，报告显示 3/5，点开就知道是哪 2 条红的。

记住这句话：一条断言 = 一个 pm.test。 名字写清楚"在验什么"，不要写"检查1""检查2"。

4能断言什么：全景表

左边是"你想验证的事"，右边是照抄就能用的写法

想验证写法
状态码pm.response.to.have.status(200)
状态码是几个之一pm.expect(pm.response.code).to.be.oneOf([200, 201])
响应时间（毫秒）pm.expect(pm.response.responseTime).to.be.below(2000)
响应大小（字节）pm.expect(pm.response.responseSize).to.be.below(102400)
某个响应头存在pm.response.to.have.header("Content-Type")
响应头内容pm.expect(pm.response.headers.get("Content-Type")).to.include("application/json")
返回是合法 JSONpm.response.to.be.json
取响应体（解析成对象）const b = pm.response.json()
字段等于某个值pm.expect(b.id).to.eql(1)
字段是数字类型pm.expect(b.id).to.be.a("number")
字段是字符串类型pm.expect(b.title).to.be.a("string")
对象里有某个字段pm.expect(b).to.have.property("userId")
数组长度正好 10pm.expect(arr).to.have.lengthOf(10)
数组不为空pm.expect(arr.length).to.be.above(0)
字符串包含某段文字pm.expect(b.title).to.include("sunt")

三类断言，重要性递增

协议断言→ 结构断言→ 业务断言（最值钱）
层次验证什么例子
协议断言请求通不通状态码 200、响应时间 < 2s
结构断言返回的格式对不对是数组、长度 10、字段类型是 number
业务断言数据本身对不对每条数据的 userId 都等于 1

为什么业务断言最值钱 —— 一个真实例子：

你请求 /posts?userId=1，想查"用户 1 的帖子"。假设过滤条件失效了，接口返回了 10 条别人的帖子。此时：

状态码 200 ✅　条数 10 条 ✅　字段 齐全 ✅

前两类断言全部通过，接口却是错的。只有"每条数据的 userId 都等于 1"这条业务断言能抓住它。

这就是面试里能把你和别人区分开的那句话：技术断言验证接口通不通，业务断言验证业务对不对。

这个免费 API 还给了个现成的反面教材：请求 /posts?userId=abc（传字母给一个应该是整数的参数），它不报 400，返回 200 + 空数组。

如果你只写"状态码是 200"，这条用例会显示通过，而真相是这个接口根本没做参数类型校验。这就是"200 不等于通过"。

5pm.expect 速查

语法就一句话：expect(实际值).to.某某(期望值)

Postman 的 pm.expect 用的是 Chai 这个断言库。它的语法设计成接近英文句子：

pm.expect(pm.response.responseTime).to.be.below(2000);
// 读作：期望 响应时间 是 小于 2000
写法意思例子
.to.eql(x)等于（对象、数组也能比）.to.eql(1)
.to.equal(x)严格等于（比类型）.to.equal("abc")
.to.be.above(n)大于.to.be.above(0)
.to.be.below(n)小于.to.be.below(2000)
.to.be.at.least(n)大于等于.to.be.at.least(1)
.to.be.a("number")是某种类型number / string / array / object / boolean
.to.include(x)包含字符串含某段、数组含某元素
.to.have.property("k")有某个字段.to.have.property("title")
.to.have.lengthOf(n)长度是 n.to.have.lengthOf(10)
.to.be.true为真直接跟，不用括号
.to.be.oneOf([...])是其中之一.to.be.oneOf([200, 201])
.to.not.eql(x)不等于（取反）.to.not.eql(0)

记忆法：.to. 后面就是一句英文小句子。把 pm.expect(这里) 里的东西当主语，读一遍就知道对不对。

不用背全表。写的时候看着这张表抄，写十几次就自然记住了。

pm.expect 还可以加一句"失败说明"

pm.expect(item.userId, "第 " + (index + 1) + " 条的 userId").to.eql(1);

第二个参数是失败时显示的文字。在循环里特别好用 —— 100 条数据里有一条错了，它会直接告诉你是第几条，而不是只丢给你一句"expected 5 to equal 1"。

6完整脚本：5 条断言

照抄进 After response，直接就能跑

请求：GET https://jsonplaceholder.typicode.com/posts?userId=1

接口真实行为（已实测）：返回 200，一个长度 10 的数组，每条数据的 userId 都等于 1，id 从 1 到 10。

// 先解析响应体，存成变量，后面反复用
const body = pm.response.json();

// ① 协议断言：状态码是 200
pm.test("状态码是 200", function () {
    pm.response.to.have.status(200);
});

// ② 协议断言：响应时间小于 2 秒
pm.test("响应时间小于 2000ms", function () {
    pm.expect(pm.response.responseTime).to.be.below(2000);
});

// ③ 结构断言：返回的是数组，且正好 10 条
pm.test("返回 10 条数据", function () {
    pm.expect(body).to.be.an("array");
    pm.expect(body).to.have.lengthOf(10);
});

// ④ 业务断言：每一条的 userId 都必须是 1  ← 最重要的一条
pm.test("每条数据的 userId 都是 1", function () {
    body.forEach(function (item, index) {
        pm.expect(item.userId, "第 " + (index + 1) + " 条的 userId").to.eql(1);
    });
});

// ⑤ 结构断言：字段齐全，且类型正确
pm.test("字段齐全且类型正确", function () {
    body.forEach(function (item) {
        pm.expect(item).to.have.property("id");
        pm.expect(item).to.have.property("title");
        pm.expect(item).to.have.property("body");
        pm.expect(item.id).to.be.a("number");
        pm.expect(item.title).to.be.a("string");
    });
});

点 Send，预期看到 5/5。

为什么第 ④ 条要写成循环？

因为 pm.expect(body.userId) 是错的 —— body 是个数组，本身没有 userId 这个字段。你必须逐条拿出来看：body.forEach(function (item) { ... })。

这是初学者最常踩的一个坑：响应是数组时，断言要写在循环里。

再练一次"让它红"：把第 ③ 条的 lengthOf(10) 改成 lengthOf(5)，Send，看它变红。

再把第 ④ 条的 to.eql(1) 改成 to.eql(2)，Send —— 这次你会看到失败信息里带着"第 1 条的 userId"，这正是那句自定义说明在起作用。

7怎么看结果 + Console 调试

断言失败之后，正确的第一步是看哪里

响应区那一排会多出一个 Test Results 标签页，上面的数字是 通过数 / 总数：

显示含义
5/55 条全过
3/5过了 3 条，2 条挂了
根本没有这个标签页脚本里一条 pm.test 都没跑 —— 要么没写，要么写在了 pm.test 外面，要么语法报错

点开 Test Results，每条断言一行：绿勾 = 过，红叉 = 挂。红的那条展开，会看到三样东西：

  1. 失败原因：AssertionError: expected 201 to equal 200
  2. 是哪一行：直接指出代码位置
  3. 你写的那句失败说明（如果加了第二个参数）

Console：断言写之前先看一眼实际值

Postman 左下角有个 Console 按钮。脚本里的 console.log() 输出全都在这儿。

const body = pm.response.json();

console.log("返回条数：", body.length);
console.log("第一条：", JSON.stringify(body[0]));

点 Console 打开面板 → Send → 就能看到输出。

为什么这个很重要？

写断言时你经常不知道实际值到底是 1 还是 "1"、是数组还是对象。硬猜然后反复试，很慢。

正确做法是先 log 出来看一眼，再写断言。

面试点：问到"断言失败了你怎么排查"，答案里应该有 "看 Postman Console 里打印的实际响应值，和接口文档对照"。

8Snippets 与批量跑

一个是"不用背语法"，一个是"断言的真正价值"

Snippets：点一下，代码自动出现

After response 页面右侧那一列，是 Postman 准备好的常用代码片段。点一下，它就自动插到你的光标位置。

Snippet 名字插入什么
Status code: Code is 200状态码等于 200 的断言骨架
Status code: Successful POST request状态码是 201 或 202
Response body: JSON value check取响应体里某个字段做检查
Response body: Contains string响应体包含某段文字
Response time is less than 200ms响应时间断言

用法：先点 Snippet 生成骨架，再把里面的值改成你想要的。比自己从零打快，也不容易记错语法。

Collection Runner：批量跑

你不可能每次都手动点一遍 Send。真正干活时是这样跑的：

① 存进集合请求命名成用例名
② 打开 Runner集合上右键 Run collection
③ 选请求勾上要跑的
④ 点 Run一键全跑
⑤ 看汇总通过/失败/耗时

跑完会给你一份汇总：总共跑了多少条请求、多少条断言通过、多少条失败，失败的是哪些。

这才是断言的真正价值。

100 条请求一键跑完，你不可能一条条用眼睛看。有了断言，机器在几秒内告诉你"哪几条挂了、挂在哪一句"。

面试里"你怎么做接口回归测试"的标准答案，就是这一段。

9九个常见的坑

都是会真实撞上的，撞上回来看这张表

坑你会看到什么怎么解
数字和字符串不分 expected '1' to equal 1 先 console.log 看实际类型。1（数字）和 "1"（字符串）在断言里不是一回事
断言没包进 pm.test Test Results 没动静 / 不出现 所有断言必须写在 pm.test("名字", function(){ ... }) 里面
对数组直接取字段 Cannot read properties of undefined 响应是数组时要 forEach 逐条判断
响应不是 JSON 却调 json() Unexpected token 先加 pm.response.to.be.json 单独验一条，或改用 pm.response.text()
只断言状态码 全绿，但数据是错的 补业务断言：字段值、条数、类型
断言名字没意义 报告里全是"检查1""检查2" 名字写清"在验什么"，报告才看得懂
把测试数据写死在脚本里 换个环境整套挂掉 用环境变量 pm.environment.get("...") 代替硬编码
脚本改完没保存 下次打开是空的 Ctrl+S 保存，标签上有个小圆点提示未保存
响应时间阈值写太紧 偶尔红一次，重跑又绿 阈值给宽容一点（比如 2000ms），不然网络抖动就会误报

最后一条多说一句：偶发失败比稳定失败更麻烦，因为它会让你怀疑自己。

真实工作里，性能类断言（响应时间）的阈值一般会留出很大余量，或者根本不放在功能测试里跑。面试时能说出这一点，是加分项。

10本讲的自测题

先自己开口答，再展开对答案

Q1　视频教程里那个 Tests 标签，在你这个版本里叫什么？在哪一步点开？

叫 Scripts，点开后左边那一列里的 After response。

Q2　为什么建议每条断言单独包一个 pm.test，而不是全写在一个里面？

一个 pm.test 里第一条挂了，后面的就不跑了，你只知道"有问题"，不知道是哪一个字段错。分开写则全部跑完，报告里能精确定位。

Q3　一个接口返回 200，但返回的数据是错的。哪一类断言能抓住它？为什么只写状态码断言的用例会"通过"？

只有业务断言能抓住。状态码 200 只说明"服务器处理成功了"，不代表数据正确。请求 /posts?userId=abc 返回 200 + 空数组，就是"200 不等于通过"的真实例子。

Q4　响应体是一个数组，你想验证"每一条的 userId 都等于 1"，脚本该怎么写？

用 body.forEach(function (item) { pm.expect(item.userId).to.eql(1); }) 逐条判断。直接写 body.userId 会报 undefined，因为数组本身没有这个字段。

Q5　你新写了一条断言，跑出来是绿的。怎么确认它真的在工作？

故意把期望值改错，重跑，看它会不会变红。一个从没见过失败的断言，你没法确定它在跑。

Q6　断言失败了，你的排查顺序是什么？

① 看 Test Results 里的失败原因和行号 → ② 用 console.log 把实际值打到 Postman Console 看 → ③ 和接口文档对照，判断是断言写错了还是接口真有问题。

Q7　pm.expect(item.userId, "第 " + index + " 条").to.eql(1) 里第二个参数是干什么的？

失败时显示的说明文字。在循环断言里用它，能直接告诉你是第几条数据出了问题。

Q8　面试问"你怎么做接口回归测试"，怎么答？

把用例存进 Collection，每条接口下写断言，然后用 Collection Runner 批量执行，看汇总报告里哪些请求、哪些断言失败。重点说"断言替人做判断"这个分工。
