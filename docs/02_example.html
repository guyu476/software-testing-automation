接口测试 · 完整实战案例

一条接口，做一次真正的测试

前面讲了概念，这份文件把一次完整的接口测试从头到尾走一遍。被测对象是公开练习 API JSONPlaceholder，不需要注册、不需要账号，你照着做就能跑通。

下面每一条「预期结果」都是真实请求验证过的，不是猜的。你会看到它每一个参数、每一种取值实际返回什么。

这次测试的五个步骤

  1. 1先读接口文档
  2. 2设计用例（10 条）
  3. 3逐条执行，记录结果
  4. 4写断言，让机器判定
  5. 5批量跑 + 出结论

1先读接口文档

不读文档就开始点，是接口测试最常见的坏习惯。

真实工作里，你拿到的是一份接口文档（Swagger、Wiki、或者 Word）。这里我把它简化成一份，内容跟真实的等价：

项目内容
接口名称查询帖子列表
请求方法GET
请求地址https://jsonplaceholder.typicode.com/posts
请求参数userId：查询参数（query），可选，整数。按用户 ID 过滤帖子
成功返回200，JSON 数组，每个元素含 userId / id / title / body
失败返回404，路径不存在

注意这份文档少了什么。它没说——

① userId 传非数字（比如 abc）会怎么样？
② 传一个不存在的用户 ID 会怎么样？
③ 传负数、传 0 会怎么样？
④ 不传 userId 时返回什么？

这四点文档没写，就是你要去问开发、或者自己测出来确认的地方。真实工作里这一步叫"接口文档评审"——在开发动手前把歧义问清楚，比测出来再打回去改便宜得多。

关键认知：接口文档只告诉你"接口应该什么样"。测试的任务是验证"它实际是不是这样"。文档没写清的部分，就是这次测试的风险点，也是你能在评审会上体现价值的地方。

不用打开 Postman，先在纸上把要测什么想清楚。

拿到一条接口，按这六类去思考，基本不会漏。下面这张表就是这次测试的全部用例：

#类别用例说明请求预期结果

3逐条执行：真实结果出来了

这一节是整份文件的核心。看第 6–9 条实际返回了什么。

3.1 先说怎么在 Postman 里做

每一条用例，就是一次独立的请求。做法：

  1. 地址栏填上面的 URL，方法保持 GET，点 Send
  2. 看状态码和响应体，跟我下面记录的结果对比
  3. 每测完一条，点地址栏右边的 Save 保存下来，命名成用例名（如"查userId=1的帖子"）

暂时都保存进你那个 My Collection 里就行。10 条都存下来之后，你就有了一个真正的"接口用例集"。

3.2 执行结果（真实记录）

#请求实际状态码实际返回结论
1/posts200数组，100 条符合
2/posts?userId=1200数组，10 条，id 为 1–10符合
3/posts?userId=1200数组，10 条符合
4/posts?userId=10200数组，10 条符合
5/posts?userId=11200[] 空数组符合
6/posts?userId=abc200[] 空数组存疑
7/posts?userId=-1200[] 空数组存疑
8/posts?userId=200[] 空数组存疑
9/posts?userId=999200[] 空数组符合
10/postss404—符合

3.3 最重要的发现：第 6、7、8 条

看第 6 条。你传了一个字母 abc 给一个"应该是整数"的参数，接口返回的是——

状态码：200 OK
响应体：[]

没有报错。没有 400。没有告诉我"参数格式不对"。它就像什么都没发生一样，还我一个空数组。

第 7 条（负数 -1）、第 8 条（空值）一模一样，全是 200 + []。

这就是为什么"看状态码判断通过"是错的。

如果你只看状态码，这 8 条用例全是 200，全部"通过"——你会得出"这个接口没问题"的结论。

但实际上，它根本没做参数校验。用户传了 abc，它不去检查这个值合不合法，而是直接拿去查询，查不到就返回空数组，全程 200。

状态码 200 掩盖了一个真实存在的缺陷。

3.4 那这到底算不算 Bug？

这是个好问题，答案能体现你的测试思维：

判断依据结论
如果接口文档写了"userId 必须是整数，非整数返回 400"是 Bug。实际结果（200）≠ 期望结果（400）
如果文档只写了"userId 可选，整数"，没写非法值怎么处理文档缺失。要去问产品/开发，明确期望行为。这是"待确认"，不是直接判 Bug
如果这是内部接口，调用方一定是前端，前端保证只传整数可能是设计如此，风险等级低。但仍建议补校验，防止有人绕过前端直接调

面试可以直接用这段："判断一个问题是 Bug 还是设计如此，不能凭感觉，要看依据。我的判断顺序是——先查接口文档有没有明确约定；文档没写就问产品确认期望行为；确认了期望、实际又不符，才是缺陷。如果文档缺失，我会先把这个当成风险点提出来，而不是直接开单——因为开一张没依据的 Bug 单，会被开发打回来，还损害自己的信誉。"

这段话的杀伤力在于：它证明了一个人有"缺陷判定的依据意识"，而不只是"看到不对劲就喊 Bug"。

4写断言：让机器替你判断

前面 10 条你是用眼睛看的。现在教机器怎么看。

4.1 先看主用例：第 2 条

打开你保存的「查 userId=1 的帖子」这条请求，点 Tests 标签页，把下面整段贴进去，然后 Send。

// 先把响应体解析成能点属性出来的对象
var jsonData = pm.response.json();

// ① 状态码断言
pm.test("状态码是 200", function () {
    pm.response.to.have.status(200);
});

// ② 返回条数断言
pm.test("返回 10 条数据", function () {
    pm.expect(jsonData.length).to.eql(10);
});

// ③ 业务断言：每一条的 userId 都必须是 1
pm.test("每条数据的 userId 都是 1", function () {
    jsonData.forEach(function (item) {
        pm.expect(item.userId).to.eql(1);
    });
});

// ④ 结构断言：字段都得在
pm.test("每条数据都包含 id / title / body 字段", function () {
    jsonData.forEach(function (item) {
        pm.expect(item).to.have.property("id");
        pm.expect(item).to.have.property("title");
        pm.expect(item).to.have.property("body");
    });
});

// ⑤ 响应时间断言
pm.test("响应时间小于 2 秒", function () {
    pm.expect(pm.response.responseTime).to.be.below(2000);
});

Send 之后，切到 Test Results 标签页，你会看到 5 行绿色结果。

现在逐行解释这 5 条断言，为什么是这 5 条：

① 状态码 —— 最基础的一层，验证 HTTP 通信正常。但单独它一个远远不够。

② 条数 —— 验证返回的数据量对不对。userId=1 应该有 10 条，如果返回 8 条或 100 条，说明过滤逻辑坏了。

③ 业务断言（最关键） —— 验证过滤条件真的生效了。这一条很多人会漏。

④ 结构断言 —— 验证字段完整性。前端要用的字段如果没返回，页面就会崩。

⑤ 响应时间 —— 验证性能没有明显劣化。

第 ③ 条为什么最关键，举个反例你就懂了：

假设接口有个 bug，过滤条件没生效，直接返回了全库 10 条数据（只不过恰好 id 是 100–109）。那么——

状态码是 200 ✅；条数正好也是 10 条 ✅；字段也齐全 ✅。

前两条断言全过了，但这个接口是错的——它返回的压根不是 userId=1 的帖子。

只有第 ③ 条断言 每条数据的 userId 都是 1 能抓住这个 bug。这就是"技术断言"和"业务断言"的区别：前者验证接口通不通，后者验证业务对不对。

4.2 再看第 9 条：空数组的断言怎么写

「查 userId=999」这条，预期就是返回空数组。所以断言要反着写：

var jsonData = pm.response.json();

pm.test("状态码是 200", function () {
    pm.response.to.have.status(200);
});

pm.test("返回空数组，长度是 0", function () {
    pm.expect(jsonData.length).to.eql(0);
});

这里有一个很重要的认知，别搞混：

这条用例会亮绿勾、显示"通过"。但这不代表"这个接口很棒"——它代表的是"接口的实际行为和预期一致"。

「查一个不存在的用户，返回空数组」是合理的预期，所以它通过。

而第 6 条「传 abc」，如果文档约定应该报 400，那它就该是失败的——但因为我们还没确认期望，暂时只能记录现象。

所以说：断言测的是"符不符合预期"，不是"好不好"。预期从哪来？从接口文档、从需求、从产品确认里来。这就是为什么第 1 步读文档那么重要。

5批量跑，然后出结论

手工点 10 次能验证接口，但验证不了"每次发版都还好好的"。

5.1 批量执行

你刚才把 10 条请求都保存进了 Collection。现在：

  1. 左侧 My Collection 上点 ... → Run collection（或者选中集合后点 Run）
  2. 会打开 Runner 页面，里面列出这 10 条请求
  3. 直接点 Run，看着它一条条自动跑
  4. 跑完给出一张结果表：多少通过、多少失败

注意：只有写了断言的请求，Runner 才能判定它通过还是失败。没写断言的请求会显示"没有测试"，Runner 不知道该判它什么。

所以第 4 步的断言不是"高级功能"，它是批量执行的前提。这也是为什么面试官特别爱问断言——它直接区分了"会调接口"和"会做接口测试"。

5.2 这次测试的产出：一份测试记录

这才是"做了一次测试"的真正成果。不是点了 10 次 Send，而是留下这么一份东西：

项目内容
被测接口GET /posts（查询帖子列表）
用例数10 条，覆盖正常流、边界值、参数异常、业务异常、路径异常
执行结果10 条执行完毕；8 条符合预期，3 条待确认（第 6/7/8 条）
发现的问题接口对 userId 参数无类型校验：传入非数字 abc、负数 -1、空值，均返回 200 + 空数组，而非参数错误提示
风险等级中。当前前端会保证传整数，直接影响小；但接口对外开放或无前端保护时，可能产生难以排查的"查不到数据"问题
待办与开发确认 userId 非法值的期望行为；确认后在文档中补充约定

把上面这张表看懂——它就是你的第一份"接口测试报告"。面试时被问"你怎么做接口测试"，你完全可以说：

"我做过一个完整的练习：拿一条查询接口，设计了 10 条用例覆盖正常流、边界值、参数异常和业务异常。执行中发现它对参数类型没有校验，传非数字也返回 200 空数组。我判断这属于文档缺失而非明确缺陷，所以先记录为风险点，同时给主用例写了 5 条断言——状态码、返回条数、业务字段值、字段结构、响应时间——用 Collection Runner 做批量回归。"

这段话里每一个细节都是真的，而且每一句都在展示你的水平。它比背十道面试题有用得多。

5.3 如果还想再深一步

下面三件事做完，你这个案例就彻底完整了：

动作怎么做学到什么
把 baseUrl 抽成变量建一个 Environment，定义 baseUrl，把 10 条请求的地址换成 {{baseUrl}}/posts环境变量怎么用，为什么它是回归的前提
给第 5 条也加断言越界 userId=11，断言"状态码 200 且返回空数组"异常场景的断言怎么设计
故意弄坏一条断言把"返回 10 条"改成"返回 5 条"，重新 Send 和 Run亲眼看到断言失败长什么样，学会区分"用例失败"和"接口坏了"

最后一条特别重要。很多人写的断言永远是绿的，因为他们没验证过断言能不能变红。一个不会失败的断言，等于没有断言。

5.4 自测题

写下你对这 5 题的答案，再展开对照

Q1：为什么只看状态码 200 不能判断接口测试通过？用这次案例举一个具体例子。

要点：用第 6 条举例——传 userId=abc，接口返回 200 + 空数组，状态码完全正常，但实际是参数校验缺失。再补一个更有说服力的：如果过滤逻辑失效返回了错误的数据，状态码照样是 200，只有业务断言能抓住。

Q2：什么是"业务断言"？它和"技术断言"有什么区别？

要点：技术断言验证接口通不通（状态码、响应时间、字段存在）；业务断言验证业务对不对（如"每条数据的 userId 都是 1"）。举例说明：如果过滤条件失效但恰好返回 10 条数据，技术断言全过，只有业务断言能发现。

Q3：测出"传 abc 返回 200 空数组"，你会直接开 Bug 单吗？

要点：不会直接开。先查接口文档有没有约定非法值的处理方式；没写就去问产品/开发确认期望行为；确认了期望又不符，才是缺陷。没依据的单子会被打回来。

Q4：断言都亮绿勾，是不是说明接口没问题？

要点：不是。绿勾只说明"实际结果符合预期"。如果预期本身写错了（比如把错误的期望值写进断言），接口有问题也照样亮绿。断言测的是符不符合预期，不是好不好。

Q5：为什么没有断言的接口用例，批量执行结果没有意义？

要点：Runner 没有判定依据，只能显示"没有测试"，无法给出通过/失败统计。断言的本质是把你心里的"验收标准"翻译成机器能判断的语句——没有它，批量跑 100 条你还是要一条条肉眼看，等于没自动化。
