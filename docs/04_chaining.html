接口测试 · 接口关联详解

接口关联：把上一个接口的响应，喂给下一个接口

单个接口测通了，不代表会测业务流。真实工作里的接口测试绝大部分是串起来跑的 —— 先登录拿 token，再用 token 调业务接口；先创建拿 id，再用 id 查详情。把这条链子接起来的技术，就叫接口关联。

这份文件里两个例子的所有接口返回，都是先在你本机真实请求验证过的，不是编的。练习对象：公开 API httpbin.org 与 JSONPlaceholder，都不用注册。

1什么是接口关联，为什么非做不可

先看清它在真实工作里的位置

定义一句话：上一个接口的响应内容，是下一个接口的输入参数 —— 这两个接口天然有先后依赖，不能单独测，必须串起来。这个"串"的动作就是接口关联（也有人叫"关联传参""参数传递"）。

真实工作里到处都是这种依赖：

业务场景请求 1 给出什么请求 2 拿它干什么
登录token后续每个接口都要带在请求头里
提交订单orderId用它查订单详情、发起支付、取消订单
上传头像fileId用它把文件绑定到用户资料上
提工单issueKey用它去评论、流转状态、关闭
批量造数据一批新建记录的 id逐个去查详情、去删除（清理数据）

为什么它是分水岭

「调通一个接口」和「测一个业务流」之间隔着的就是这件事。只会单接口 = 只会点 Send；会关联 = 能测一个完整业务场景。面试里问"你做过接口自动化吗"，能答上来的通常就是这一块。

不这么做会怎样

假设你测登录后的业务接口，需要带 token。最省事的做法是把 token 直接写死在请求头里：

写死 token（坏例）用关联（好例）
怎么填请求头手填 Bearer eyJhbGci...请求头填 Bearer {{token}}
token 几小时后过期全部用例 401 集体失败，你得手工换一遍重跑一次登录请求，自动换新
换测试环境token 是另一个环境的，不通切环境，变量自动变
批量跑 100 条用例跑一半过期，后面全红先跑登录，后面自动带上
能不能进 CI不能，要人工维护能，全自动

一句话记住：凡是会"变"的东西，都不能写死。token 会变、id 会变、时间戳会变 —— 这些都必须靠关联传递。

2关联只有三个动作：取 → 存 → 用

所有关联，不管多复杂，都是这三步

① 取从上一个接口的响应里，把那个值拿出来
② 存把它存进一个变量，起个名字
③ 用在下一个接口里用 {{名字}} 引用它

三步各自的写法，就这么点东西：

// ① 取 —— 写在第一个请求的 Scripts → After response 里
var res = pm.response.json();   // 把响应体解析成 JS 对象
var token = res.json.token;     // 按路径把值取出来

// ② 存 —— 还是写在同一个地方，紧挨着上一行
pm.environment.set("token", token);   // 存进环境变量，名字叫 token

// ③ 用 —— 这部分不在脚本里，写在第二个请求的界面上
//    请求头里填：  Authorization = Bearer {{token}}
动作写在哪关键代码
① 取请求 1 的 After responsepm.response.json() + 字段路径
② 存请求 1 的 After responsepm.environment.set("名", 值)
③ 用请求 2 的地址 / 请求头 / 请求体里双大括号 {{token}}

双大括号是 Postman 的"插值"语法

你在请求里写 {{token}}，Postman 发出去之前会先把它替换成变量的真实值。所以服务器收到的是真实 token，它根本不知道你用没用什么变量。

这个替换动作发生在发送的那一刻。所以改了变量的值，必须重新 Send 才会生效 —— 这点跟断言一样。

为什么要在"第一个"请求存，而不是在"第二个"请求里取

因为请求 2 拿不到请求 1 的响应。每个请求的 pm.response 只代表自己的那次响应，脚本跑完就过去了。所以值必须在请求 1 那里就"存起来"，请求 2 才有东西可用。

这也解释了第 3 节那个坑为什么最容易踩：存错地方了，值活不到下一个请求。

3变量存在哪里（第一个大坑）

存错地方，值就传不过去 —— 这是初学者最常卡住的一步

Postman 有四种变量，写法长得几乎一样，但能活多久差别巨大：

类型怎么写能跨请求吗什么时候用
局部变量pm.variables.set()不能只在当前这一次请求里临时用
环境变量pm.environment.set()能关联首选，切换环境时自动换值
集合变量pm.collectionVariables.set()能只在某个集合内部用的值
全局变量pm.globals.set()能所有集合都要用的值（少用，容易乱）

最大的坑：pm.variables.set() 不能用来做关联

它的名字最"通用"，所以最容易顺手就用了。但它是局部变量，只在当前这个请求的执行过程中存活 —— 脚本跑完就没了。

结果就是：请求 1 里你明明存了，请求 2 里却取不到，你盯着两段一模一样的代码看半天，找不出哪里错了。

做关联，一律用 pm.environment.set() 或 pm.collectionVariables.set()。

环境变量 vs 集合变量，到底选哪个

选谁什么时候
环境变量这个值会随环境变，或者你要用它切环境（测试环境 / 预发 / 生产各一套 token、域名）
集合变量这个值只在这个集合内部有意义，跟环境无关（比如从列表接口取到的临时 id）

拿不准就用环境变量，后面切换环境时你会庆幸。
本讲的例子 A（token）用环境变量，例子 B（id）用集合变量，两种都让你碰一次。

4例子 A：登录 → 取 token → 带 token 访问

最接近真实工作的那条链

先看这条链要串成什么样：

POST /post
（模拟登录，提交用户名和 token） → 取响应里的 json.token → 存进环境变量 {{token}} → GET /bearer
请求头带 Bearer {{token}}

先看我实测出来的真实行为

我把这条链上的接口先在你机器上跑了一遍，结果如下 —— 所以你知道下面每个"预期结果"都是真的：

请求状态码返回
GET /bearer 不带 Authorization 头401—（未授权）
GET /bearer 带 Authorization: Bearer abc123200{"authenticated": true, "token": "abc123"}
GET /bearer 带 Authorization: Bearer （token 为空）401—（未授权）
POST /post，请求体 {"username":"tester","token":"tok_abc123"}200响应里有 json.token = "tok_abc123"

注意最后一行：httpbin 会把你提交的 JSON 原样放在响应的 json 字段里还给你。所以取 token 的路径是 res.json.token（两层：先 json，再 token）。这一层是新手最常写错的地方。

同时注意前两行：不带 token → 401，带上 → 200。这就是一个自带鉴权的接口，正好用来演示关联。

步骤 1：建一个环境，放两个变量

  1. 左边竖栏（跟你之前看到的 COLLECTIONS 并排的那几个入口）里找到 Environments
  2. 点 + 新建，名字随便起，比如 api-test
  3. 在表格里加两行：
VariableValue
hb_urlhttps://httpbin.org
token（留空 —— 等脚本自动填进去）
  1. 保存（Ctrl+S）

最容易漏的一步：回右上角的下拉框，选中 api-test

你右上角原先显示的是 No environment。建完环境不等于已经在用它，必须点那个下拉把它选中。

没选中的话，pm.environment.set() 会直接报错，`{{hb_url}}` 也不会被替换 —— 你会看到地址栏里赫然写着 {{hb_url}}/post，请求当然失败。

步骤 2：请求 1 —— 模拟登录

项目填什么
方法POST
地址{{hb_url}}/post
Body选 raw，右边选 JSON
Body 内容见下
{
  "username": "tester",
  "token": "tok_abc123"
}

步骤 3：请求 1 的 After response 脚本（取 + 存 + 验证）

位置还是你熟悉的那个：Scripts → 左边那一列的 After response。整段贴进去：

// ① 取
var res = pm.response.json();     // 整个响应体
var token = res.json.token;       // 两层：先 json，再 token

// ② 存
pm.environment.set("token", token);

// ③ 自检：确认真的取到了（这一步千万别省，理由见第 7 节）
pm.test("状态码是 200", function () {
    pm.response.to.have.status(200);
});

pm.test("响应里取到了 token", function () {
    pm.expect(token, "token 字段").to.be.a("string").and.not.empty;
});

// 打印出来看一眼，出问题时有据可查
console.log("我取到的 token =", token);

先单独 Send 这一个请求，确认底部 Test Results 是 2/2。然后打开 Console，应该能看到 我取到的 token = tok_abc123。

步骤 4：请求 2 —— 带着 token 访问

把这个请求也存进你的集合里（和请求 1 放同一个 Collection），然后：

项目填什么
方法GET
地址{{hb_url}}/bearer
Headers加一行：Key = Authorization，Value = Bearer {{token}}

注意 Bearer 后面有一个空格，再跟 {{token}}。这个格式是 HTTP 鉴权的标准写法，少了空格服务器认不出来。

Header 的 Key 和 Value 就是你在 Params 那一页学过的同一套东西 —— 名字 = 内容。

步骤 5：请求 2 的断言

var res = pm.response.json();

pm.test("状态码是 200（鉴权通过）", function () {
    pm.response.to.have.status(200);
});

pm.test("服务器认出了我的 token", function () {
    pm.expect(res.authenticated, "authenticated").to.eql(true);
});

// 最强的一条：服务器回显的 token，必须等于我环境变量里存的那个
pm.test("回显的 token 和我存的一致", function () {
    pm.expect(res.token).to.eql(pm.environment.get("token"));
});

Send 之后，预期：状态码 200，响应体 {"authenticated": true, "token": "tok_abc123"}，Test Results 3/3。

先跑请求 1，再跑请求 2 —— 顺序不能反。如果先跑请求 2，{{token}} 还是空的，你必然收到 401。这不是接口坏了，是链子没接上。

步骤 6：反证 —— 证明 token 真的是从请求 1 传过来的

这一步绝对不能跳过，跟上一步"故意改坏看变红"是同一个道理：你没见过它失败，就不知道它是不是真的在工作。

  1. 打开 Environments，把 token 的值清空（删干净，保存一个空值）
  2. 回到请求 2，Send

预期：状态码 401，断言全部失败。

这说明服务器读到的确实是你变量里的那个值 —— 变量一空，请求头就退化成 Bearer （前缀后面什么都没有），服务器立刻拒绝，关联链路成立。

不要用「把 token 改成一个错误的值」来反证 —— 那样不会失败。

实测过：httpbin 的 /bearer 只检查请求头里有没有 Bearer 这个前缀、前缀后面是不是空的，根本不校验 token 的内容对不对。所以填 Bearer wrong_token 照样返回 200。

真正会返回 401 的只有三种情况：① 变量清空（退化成 Bearer ）；② 把 Headers 里 Authorization 那一行的勾取消（等于完全不发这个头）；③ 忘了写 Bearer 前缀，直接填了裸 token。任选一种做反证都行。

  1. 改回来（重新跑一次请求 1，让脚本把真的 token 写回变量）→ 再跑请求 2，恢复 200

5例子 B：列表 → 取 id → 查详情

"从数组里取一个值"是这个例子的真正考点

GET /posts
100 条列表 → 取第一条的 id（数组里取值） → GET /posts/{{postId}}
查这条详情

真实工作里更常见的是反过来（先创建再查），但这个链路最好演示，而且"从数组里取值"的写法你必须会。

先看实测数据

请求状态码返回
GET /posts200数组，100 条，第一条 id = 1
GET /posts/1200{"userId":1,"id":1,"title":"sunt aut facere...","body":"quia et suscipit..."}

请求 1：GET {{jp_url}}/posts

先在环境里加一个变量：jp_url = https://jsonplaceholder.typicode.com。

var body = pm.response.json();

pm.test("状态码是 200", function () {
    pm.response.to.have.status(200);
});

pm.test("返回的是数组，而且不为空", function () {
    pm.expect(body).to.be.an("array").that.is.not.empty;
});

// 取第一条的 id —— 注意数组是 body[0]，不是 body
var firstId = body[0].id;

// 存进集合变量（这个值只在本集合内用，所以用集合变量就够）
pm.collectionVariables.set("postId", firstId);

console.log("存进去的 postId =", firstId);

写错对照：body.id 和 body[0].id 的区别

响应是数组的时候，body.id 是 undefined —— 因为数组本身没有 id 这个字段，只有它里面的元素才有。

这个错的表现是：变量存进去是空的（甚至直接报错），请求 2 用不了。判断响应是对象还是数组，看响应体第一个字符：{ 是对象，[ 是数组。

请求 2：GET {{jp_url}}/posts/{{postId}}

var post = pm.response.json();
var savedId = pm.collectionVariables.get("postId");

pm.test("状态码是 200", function () {
    pm.response.to.have.status(200);
});

pm.test("查到的详情 id，和上一步存的 postId 一致", function () {
    // ⚠️ 关键：变量取出来是【字符串】，响应里是【数字】，必须转一下再比
    pm.expect(post.id).to.eql(Number(savedId));
});

pm.test("详情里的必填字段都在", function () {
    pm.expect(post.title).to.be.a("string").and.not.empty;
    pm.expect(post.body).to.be.a("string");
});

这里藏着第二个大坑：变量永远存成字符串

Postman 的变量不管你存进去的是数字还是布尔值，取出来永远是字符串。

所以：响应里的 post.id 是数字 1，而 pm.collectionVariables.get("postId") 取出来是字符串 "1"。如果你直接 .to.eql(savedId)，断言会失败，报错大概是：

AssertionError: expected 1 to deeply equal '1'

两个值看起来一模一样，但它不公平。解法就是上面那样加 Number()，或者用 == 而不是 to.eql。

这个坑如果你没听过，会以为是接口返回错了 —— 其实是你自己在类型上吃了亏。想确认类型，就在脚本里 console.log(typeof savedId)。

6取值写法速查表

"取"这一步的所有常见写法，照着抄

想拿什么怎么写
整个响应体（解析成对象）var res = pm.response.json();
顶层字段pm.response.json().token
嵌套对象（两层）pm.response.json().json.token
数组第 1 个元素pm.response.json()[0].id
数组长度pm.response.json().length
数组最后一个var a = pm.response.json(); a[a.length - 1].id
数组里找符合条件的某一条pm.response.json().find(function (x) { return x.id === 5; })
响应头pm.response.headers.get("Content-Type")
状态码pm.response.code
响应时间（毫秒）pm.response.responseTime
纯文本响应（不是 JSON 时）pm.response.text()

怎么知道路径该写几层？看响应体的结构，一层一层数过去：

{
  "json": {            ← 第一层：json
    "token": "abc123"  ← 第二层：token
  }
}
// 所以写：res.json.token

拿不准的时候，先 console.log(res) 把整个响应打出来看一眼结构，比猜快十倍。

取不到值的时候，先查这几件事

  1. 路径写对了吗 —— 少一层、多一层都会变 undefined
  2. 拼写对了吗 —— token 和 Token 不一样，字段名大小写敏感
  3. 响应真的回来了吗 —— 如果请求是 404/500，响应体里根本没有你要的字段
  4. 是不是数组 —— 数组要带下标 [0]
  5. 用 console.log 打出来看 —— 别靠眼睛猜

7关联链上最容易翻车的地方

值没取到的时候，Postman 不会报错 —— 它会装作没事继续发

你很可能撞上这个现象

请求 1 因为某个原因没取到值（路径写错、字段拼错、接口返回了错误结构），变量是空的。这时候你跑请求 2，会收到 401 或者 404。

然后你就开始查：接口是不是挂了？token 是不是过期了？网络是不是有问题？—— 全查错了方向。

真正发生了什么

如果 {{token}} 这个变量根本不存在或为空，Postman 不会拦你、不会报错，它会把这四个字符 {{token}} 原样发给服务器。

于是服务器收到的请求头是：Authorization: Bearer {{token}} —— 一个语法都对、内容完全无意义的 token。服务器只能说：不认识，401。

现象是"鉴权失败"，根因是"变量没取到"，中间隔了十万八千里。这就是它难查的原因。

怎么确认是这个原因

在请求 2 的 After response 里加一行，把变量打出来：

console.log("环境里的 token =", pm.environment.get("token"));
console.log("集合里的 postId =", pm.collectionVariables.get("postId"));

打开 Console 看输出：

Console 显示说明怎么修
undefined变量压根没存进去检查请求 1 的脚本、检查环境选没选中、检查存变量用对了方法（第 3 节）
空字符串存进去了，但值是空的检查"取"的路径对不对（第 6 节）
有值，但请求还是失败值对了，用法错了检查 {{ }} 拼写、Bearer 后面那个空格

治本的办法：每个"取"的地方都加一条断言

规则：只要一个请求负责"产出值"，它就必须断言"我确实产出了"。

如果没有这条断言，请求 1 会显示绿勾（它自己确实成功了），请求 2 才崩 —— 报错点离故障点隔了一个请求，你就得两头跑着查。

加了这条，请求 1 当场就红，你一眼知道问题在哪。这就是"在最靠近故障的地方失败"。

// 通用的"取到值了没"断言模板，把变量名和值换掉就能用
pm.test("上一步要用的值取到了", function () {
    pm.expect(token, "token").to.be.a("string").and.not.empty;
});

pm.test("要用的 id 是有效数字", function () {
    pm.expect(Number(postId), "postId").to.be.above(0);
});

8每个请求分别该断言什么

一条关联链的完整断言清单

把第 4 节那条链拆开，每个请求的断言职责是不一样的：

请求断言什么为什么是这条
请求 1
（产出值）		状态码是 200登录/创建这个动作本身成功
取到了值，且不为空整条链的地基 —— 少了它，故障会跑到下一个请求才暴露
请求 2
（消费值）		状态码是 200带着这个值访问，被服务器接受了
业务字段正确（如 authenticated === true）不只是"通了"，是"业务判断对了"
回显值 == 我传的值证明传的确实是我取到的那个，而不是碰巧也能通

最后那条"回显值 == 我传的值"是最有价值的一条

因为它是唯一能证明关联真的成立的断言。没有它，你可能传了个默认值/空值，接口照样返回 200，你还以为关联做对了。

这也解释了为什么第 4 节步骤 6 要手工把 token 改坏 —— 只有让"传的值"变了、结果跟着变，才能证明这条线是通的。

这条链的完整面目（串起来看）

请求 1  POST {{hb_url}}/post
  ├─ 断言：状态码 200
  ├─ 断言：取到 token，非空
  └─ 存：pm.environment.set("token", ...)
                 ↓
请求 2  GET {{hb_url}}/bearer      Headers: Authorization = Bearer {{token}}
  ├─ 断言：状态码 200
  ├─ 断言：authenticated === true
  └─ 断言：回显 token === 环境变量里的 token

9@JSONPlaceholder 的坑（必读）

不知道这个，你会白白浪费一小时

学关联，教材里最经典的例子是"创建 → 用返回的 id 去查详情"。你多半会想在 JSONPlaceholder 上试一遍：

POST /posts
创建，返回 id: 101 → 存 id = 101 → GET /posts/101 → 404

这条路在 JSONPlaceholder 上跑不通，而且不是你的错

我实测过：POST /posts 返回 {"id": 101}，看起来创建成功了。但紧接着 GET /posts/101 返回 404 未找到。

原因：JSONPlaceholder 是个假的演示接口，它不真的存数据。所有写操作（POST / PUT / DELETE）都只是"演"给你看，返回一个像模像样的响应，然后忘掉。你没有做错任何事。

你想练的链路JSONPlaceholder 上能练吗去哪练
列表 → 取 id → 查详情能（本讲例子 B）JSONPlaceholder
登录 → 取 token → 带 token 访问不能（没有鉴权接口）httpbin（本讲例子 A）
创建 → 取新 id → 查这条不能，会 404需要真存数据的服务（下一步）

所以本讲的两个例子是这么分工的

  • 例子 A（httpbin）：练"取嵌套字段 + 存环境变量 + 用在请求头" —— 最像真实工作的场景
  • 例子 B（JSONPlaceholder）：练"从数组里取值 + 存集合变量 + 用在 URL 路径" —— 读接口的典型形态

两个合起来，四种"用"的位置（请求头、URL 路径）和两种"取"的形态（对象字段、数组元素）你都练到了。真存数据的那条链，等你的 Postman 这一套练顺了，我们单独做一次。

10面试话术 + 自测题

先自己开口答，再展开对答案

被问"接口关联你是怎么做的" —— 照着说

"靠变量传递。上一个接口在 After response 脚本里用 pm.response.json() 把需要的值取出来，用 pm.environment.set() 存成环境变量；下一个接口在地址、请求头或者请求体里用双大括号引用这个变量，Postman 发送前会自动替换成真实值。"

"有两个点我会特别注意：一是不能用局部变量，pm.variables.set() 只在当前请求存活，跨不了请求；二是每个产出值的请求我都会加一条"取到值了吗"的断言，否则值没取到的时候 Postman 会把 {{token}} 原样发出去，报错点在下一个请求才暴露，很难查。"

"另外变量取出来永远是字符串，跟响应里的数字直接比较会失败，要显式转一下类型。"

这三段里，第二段和第三段是别人答不出来的部分 —— 因为它们来自踩坑，不来自背文档。

自测题

1. 用一句话说清什么是接口关联。

看答题要点

上一个接口的响应内容，作为下一个接口的输入参数 —— 两个接口有先后依赖，必须串起来跑。

加分说法：它是"单接口测试"和"业务流测试"之间的那道门槛。

2. 关联的三个动作是什么？分别用什么代码？

看答题要点

取（pm.response.json() 加字段路径）→ 存（pm.environment.set("名", 值)）→ 用（下一个请求里写双大括号 {{名}}）。

3. pm.variables.set() 能不能用来做关联？为什么？

看答题要点

不能。它是局部变量，只在当前请求的执行过程中存活，脚本跑完就没了，跨不到下一个请求。

做关联要用 pm.environment.set()（环境变量）、pm.collectionVariables.set()（集合变量）或 pm.globals.set()（全局变量）。

4. 建了环境，为什么脚本还是报错说找不到环境？

看答题要点

因为只是建了，没选中。必须回右上角那个下拉框，把环境切换成你刚建的那个（原来是 No environment）。

没选中的表现：pm.environment.set() 报错，请求里 {{变量}} 不被替换、原样显示。

5. 变量里明明存了值，下一个请求却报 401，最常见的两个原因？

看答题要点

① 值压根没存进去（存错了地方、环境没选中、取值的路径写错导致存进去是 undefined）。

② 值存进去了，但引用时变量名拼错（比如存的是 token，用的写成 {{Token}}），Postman 把没解析的 {{...}} 原样发出去，服务器自然不认。

排查方法：在 After response 里 console.log(pm.environment.get("token"))，是 undefined 还是空字符串还是正常值，一眼定位。

6. 为什么"产出值"的那个请求，必须加一条"取到值了吗"的断言？

看答题要点

因为如果不加，请求 1 会显示成功（它自己确实成功了），故障要等到请求 2 才爆发，而请求 2 报的是 401/404 这种"看起来完全无关"的错，排查成本很高。

加了之后，故障在最靠近原因的地方就暴露出来。

7. 响应是数组时，想取第一条的 id，为什么 body.id 取不到？

看答题要点

因为 body 是数组，数组本身没有 id 字段，只有里面的元素有。要写 body[0].id。

判断方法：响应体第一个字符是 [ 就是数组，是 { 就是对象。

8. 断言 pm.expect(post.id).to.eql(savedId) 失败了，但两个值肉眼看一模一样，为什么？

看答题要点

因为变量取出来永远是字符串。响应里的 post.id 是数字 1，变量取出来是字符串 "1"，to.eql 是严格比较，类型不同就不通过。

解法：pm.expect(post.id).to.eql(Number(savedId))，或改用 == 比较。

9. 为什么不能在请求头里把 token 写死？说出两条后果。

看答题要点

① token 会过期，过期后所有用例集体失败，得手工换一遍；② 换环境（测试/预发）时不通用；③ 没法接进 CI 自动跑。

一句话总结：凡是会变的东西都不能写死。

10. 你想练"创建 → 用返回的 id 查详情"，在 JSONPlaceholder 上应该期待什么结果？为什么？

看答题要点

会拿到 404。因为 JSONPlaceholder 是假的演示接口，不真的存数据：POST /posts 返回假的 {"id": 101}，但库里并没有这条记录，所以查不到。

这不是你脚本的问题。要练这条链，需要找一个真存数据的服务。

配套文件放在 api-test/ 目录下，与 db-practice/、jira/ 同一套版式。
本文档中所有接口返回（401/200、嵌套字段路径、数组条数、404 行为）均已在用户本机真实请求验证，非推测。
