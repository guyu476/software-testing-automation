接口测试学习路径（以 Postman 为工具）

这份路径按能力节点组织，不按 Postman 的功能菜单组织。按菜单学，你学完只会说"我会发请求"；按能力学，你才能回答面试官真正想问的那些问题。

先把结论摆在前面：你要学的不是 Postman，是接口测试。Postman 只是它的载体——一个能让你发请求、看响应、写断言、批量跑的工具。没有 HTTP 基础，Postman 于你就只是一排按钮。

0先搞清楚：面试到底在考什么

这一节看完，你就知道后面五讲为什么按这个顺序排。

先说一个可能不太合你预期的判断：面试官问"你会不会接口测试"，考的完全不是你会不会用 Postman。工具人人都能学，一两天的事。他真正在验证四件事：

  1. 你知不知道一个请求从发出到回来，中间发生了什么 —— 方法、地址、请求头、请求体、状态码、响应体。这是所有面试题的底座。答不出这一层，后面全是背的。
  2. 你为什么做接口测试，而不是只做 UI 测试 —— 这一题区分的是"会点按钮的人"和"理解测试分层的人"。答案跟工具无关。
  3. 你的接口用例是从哪想出来的 —— 是照着接口文档一条条抄，还是会做参数组合、边界、异常、鉴权、幂等。这一步考的是测试设计能力。
  4. 你怎么判断这个接口测过了 —— 看一眼返回 200 就算过？还是写了断言校验字段值和数据类型？这一步区分"手工调用"和"测试"。

一句话方法论：把接口测试当成隔着网络去验证业务逻辑。UI 测试是从界面上点，接口测试是绕过界面直接问后端。所以你的活儿本质没变——还是"设计用例、执行、判断对不对"，只是操作对象从按钮变成了请求。

学 Postman 之前，要先做什么？

直接回答你的问题。你不需要为学 Postman 做任何准备工作——下载、安装、打开就能点。但你要先建立三样认知，否则学了也白学：

先建立这个认知不建立的后果对应讲次
一个 HTTP 请求由哪几部分组成，响应由哪几部分组成Postman 的界面你认得每一个按钮，但不知道该填什么、填错了为什么错第 1 讲
接口测试在整个测试流程里，替代了哪一部分 UI 测试的工作面试问"你为什么做接口测试"，你只能答"因为快"第 2 讲
一次"测过了"的判定标准是什么你以为看到 200 就是通过，其实返回体里全是空数据第 4 讲

这就是为什么这份路径不从"下载 Postman"开始。先把第 1、2 讲的认知打进去，第 3 讲动手的时候你才知道自己在点的是什么。反过来，如果你现在就急着装 Postman 点两下，也不会有任何损失——但第 4 讲的断言你会看不懂。

1基础：一个请求的解剖图

这一讲是整份路径的地基。后面所有内容都是在往这张图上挂东西。

1.1 一个接口，就是"一个地址 + 一套规则"

先抛开所有术语。你在浏览器地址栏输入 https://www.baidu.com/s?wd=测试 按回车，这个过程本质上就是发了一个请求，拿到了一段响应。

把它拆开看：

部分这个例子里是什么说明
方法 MethodGET你要"干什么"——是取数据还是改数据
协议 + 域名https + www.baidu.com去哪台机器要
路径 Path/s要这台机器上的哪个功能
查询参数 Query?wd=测试带上具体条件
请求头 Header浏览器自动带的 User-Agent、Cookie 等附加信息：我是谁、我要什么格式
请求体 BodyGET 通常没有要提交给服务器的数据

这六样拼起来，就叫做一个接口请求。你平时说的"接口地址"，严格来说只是其中的第 2、3 部分，"完整接口"必须带上方法和参数。

先记住一句话：Postman 的整个界面，本质上就是把这六个部分做成六个输入框让你填。理解了这六个框，Postman 你就已经会一半了。

下面逐条讲，每一条都对应面试考点。

1.2 请求方法：GET 和 POST 的区别

这是接口测试第一高频题，几乎必问。但要小心——很多网上流传的答案其实是错的。看正确的对比：

对比项GETPOST
语义（标准定义）查询、获取数据，不改变服务器状态提交数据、创建资源，会改变服务器状态
参数放哪Query（拼在地址后面）Body（请求体里）
是否幂等幂等：调 1 次和调 100 次，服务器状态一样不幂等：调 2 次可能创建 2 条订单
能否被缓存可以默认不缓存
常见用途查列表、查详情、搜索登录、下单、提交表单、上传

面试雷区：说"GET 有长度限制、POST 没有"或"POST 比 GET 安全"。

长度限制是浏览器和服务器的实现约定，不是 HTTP 协议规定的。而安全性——两者都是明文传输（除非用 HTTPS），都能被抓包看到。POST 不比 GET 安全，只是参数不在地址栏里，不容易被人随手截图。正确说法是"POST 把参数放在请求体里，地址栏不暴露，更符合隐私场景，但不构成加密。"

这两句话说出来，面试官会知道你查过原始资料，不是背题。

除了这两个，还有三个你一定会遇到：

方法干什么幂等典型场景
GET查询是查订单列表
POST新增否创建订单
PUT全量更新是把整条用户信息替换掉
PATCH局部更新通常否只改一个昵称
DELETE删除是删除一条地址

PUT 和 PATCH 的区别（会被追问）：PUT 是"我把整条资源的新样子给你"，你只传一个字段，其他字段可能被清空；PATCH 是"我只要改这一个字段"，其他不动。测 PUT 的时候必须传全量字段，这是很常见的踩坑点。

1.3 状态码：后端给你的"一句话答复"

状态码是三位数字，第一位代表类别。你不用背全部，但下面这些必须张口就来：

状态码含义测试看到它意味着什么
200 OK成功请求通了，但不代表业务对了——见第 4 讲
201 Created创建成功新增类接口的正确返回，比 200 更精确
204 No Content成功但没有响应体常见于 DELETE 成功
301 / 302永久 / 临时重定向地址变了或需要跳转，接口测试里少见
400 Bad Request请求参数有问题参数校验类用例应该返回这个，不返回才可疑
401 Unauthorized未登录 / 未认证没带 token 或 token 无效
403 Forbidden已认证但没权限登录了，但这个角色不能干这件事
404 Not Found资源不存在路径写错，或数据确实没有
405 Method Not Allowed方法不对该用 POST 你用了 GET
429 Too Many Requests请求太频繁被限流做性能或批量脚本时常撞到
500 Internal Server Error服务端崩了测试要重点关注的：这是后端异常，通常是 bug
502 / 503 / 504网关错误 / 服务不可用 / 超时服务没起来、挂了、或响应太慢。环境问题居多，但要分辨

面试最爱追问的两组：

① 401 和 403 的区别 —— 401 是"你是谁我不知道"（认证问题），403 是"我知道你是谁，但你不许干这个"（授权问题）。

② 400 和 500 的区别 —— 400 是调用方的错（参数传得不对），500 是服务端的错（后端代码炸了）。这个区分很重要，因为它决定这个 bug 该提单给谁、算谁的责任。

1.4 请求头与响应头：藏在细节里的考点

头信息（Header）就是一堆"键: 值"。你不需要全部认识，但这几个必须知道：

Header位置作用测试关注点
Content-Type请求 / 响应说明报文是什么格式最常见的报错来源，见下方说明
Authorization请求带身份凭证登录后的接口基本上都要带
Cookie请求带会话身份老系统靠它保持登录态
User-Agent请求说明客户端是什么有的接口按客户端返回不同内容
Referer请求说明从哪个页面来的少数接口做防盗链校验
Set-Cookie响应服务端要求客户端存 Cookie登录接口返回它，后续请求才带得上

新手最常撞的坑，就是 Content-Type 没设对。你用 Postman 发一个 POST 请求，明明参数填得没错，后端一直返回 400 或报"参数为空"——十有八九是格式没对上。

两种最常见格式要分清：

application/json → 请求体长这样：{"username":"t001","password":"123456"}

application/x-www-form-urlencoded → 请求体长这样：username=t001&password=123456

接口文档上一定写了用哪种，测之前先看一眼。这个坑你踩过一次就再也不会忘。

1.5 请求体与响应体：真正的数据在这里

报文格式目前主流是 JSON。JSON 就是"键值对"，用大括号包起来，你只要看懂下面这四件事就够了：

写法叫什么例子
"key": "值"字段（字符串）"username": "t001"
"key": 123字段（数字）"age": 18
{ }对象（一个整体）"user": {"id": 1, "name": "张三"}
[ ]数组（一串）"list": [{"id":1}, {"id":2}]

注意字符串值要加引号，数字不用。这个细节在写断言的时候会经常用到——你要判断某个字段是"数字 18"还是"字符串 18"，是两个不同的断言。

一个真实的响应大概长这样（后面练习就会用到）：

部分内容
状态码200
响应体{"id": 1, "title": "标题", "userId": 1}

看到 200 就以为通过了，是新手最大的误区。如果响应体是 {"id": null, "title": ""}，状态码照样是 200，但这个接口显然是坏的。这就是第 4 讲讲断言的原因。

1.6 认证：怎么证明"我是我"

登录后的接口都要带身份凭证，否则就是 401。你只要认识这三种即可：

方式怎么带特点
Cookie + Session请求头 Cookie: JSESSIONID=xxx老系统主流。服务端存会话，客户端只存一个 ID
Token请求头 Authorization: Bearer xxx现在主流。接口测试最常打交道的就是它
签名 Sign参数里带一个算出来的 sign防篡改，常见于开放平台和支付

Token 是怎么来的？先调登录接口 → 响应里返回一个 token 字符串 → 后续每个请求把它放进请求头。Token 一般有有效期，过期了要重新登录。这正好是 Postman 环境变量的用武之地（第 3 讲）。

1.7 本讲的自测题

写下你对这 6 题的答案，再展开对照

Q1：GET 和 POST 的区别是什么？

要点：从语义（查 vs 改）、参数位置（Query vs Body）、幂等性（幂等 vs 不幂等）、缓存四个维度说。主动补一句"GET 有长度限制、POST 更安全都是不准确的说法"，这一句能把背题的人区分开：长度是服务器实现约定，安全性上两者都要靠 HTTPS。

Q2：401 和 403 有什么区别？

要点：401 是认证失败（我不知道你是谁），403 是授权失败（我知道你是谁，但你没权限）。再补一句"测试时 401 查 token 有没有带或过期，403 查账号角色有没有配错"。

Q3：接口返回 200，能不能说明这个接口测通过了？

要点：不能。200 只说明 HTTP 这一层通了。还要校验响应体里的业务字段——值对不对、类型对不对、条数对不对。这就是下一讲的断言。答出这一点，说明你真的测过接口。

Q4：PUT 和 PATCH 有什么区别？测 PUT 要注意什么？

要点：PUT 全量更新、PATCH 局部更新。测 PUT 必须传完整字段，否则没传的字段可能被清空——这是真实会出事故的地方。

Q5：接口返回 400，你会怎么查？

要点：400 是调用方的错。按顺序查：① 请求参数有没有少传或多传；② 参数类型对不对（字符串传了数字）；③ Content-Type 有没有设对；④ 参数格式（手机号、日期）符不符合要求。

Q6：登录之后调别的接口返回 401，可能是什么原因？

要点：① 没带 token；② token 带在错的位置（应该在 Authorization 头里）；③ token 过期；④ 前端格式写错（Bearer 后面有没有空格）。

这一讲最容易踩的坑：把它当"理论"跳过。第 1 讲其实是整份路径里性价比最高的一讲——面试题里的"GET/POST 区别""状态码""401 403""Content-Type"，全部在这一讲里被一次性覆盖。而且它不需要你装任何软件。

2定位：接口测试在流程里的位置

先知道自己为什么做这件事、跟谁协作、卡在哪儿，再谈工具。

2.1 测试金字塔：为什么接口测试比 UI 测试划算

这是接口测试的"存在理由"，也是面试必考。先看这张经典的分层图：

UI 测试
少 · 慢 · 脆 ↑ 接口测试
中 · 适中 · 稳 ↑ 单元测试
多 · 快 · 但开发写

越往上，越接近用户真实操作，但越慢、越不稳定、维护成本越高；越往下，越快越稳，但离业务越远。理想形状是底部宽、顶部窄的金字塔。

维度UI 测试接口测试
操作对象页面上的按钮和输入框直接发请求给后端
速度慢，一次操作要等页面渲染快，一个请求几百毫秒
稳定性差：改个按钮位置、换个浏览器、网络抖动就可能挂好：只依赖接口协议，界面改了不受影响
发现问题的时间晚，要等前端页面做完早，后端接口提测就能测
能覆盖的范围用户能看到的一切，包括样式和交互只能覆盖后端逻辑，前端渲染问题测不到
能不能定位问题难，只能看到现象容易，能直接看出是参数问题还是后端逻辑问题

面试标准答法（背这段）："接口测试相比 UI 测试有三个优势：一是介入早，后端接口开发完就能测，不用等前端页面；二是执行快、更稳定，不受页面渲染和 UI 改动影响，适合做回归；三是定位准，能直接看到请求和响应，一眼判断是前端传参问题还是后端逻辑问题。所以我们的策略是接口层做主要覆盖、UI 层只覆盖核心业务流程，也就是测试金字塔的形状。"

2.2 接口测试在流程里的位置

接口测试不是"另一种测试"，它是原来那套流程里插进来的一个环节：

需求评审Story 照旧介入，关注验收标准，同时看有没有接口层面的约定
接口文档确认API Doc 接口未开发前，先审文档：字段定义清不清楚、错误码有没有、边界怎么定
接口测试API Test 接口提测后立刻介入，比 UI 测试早一个阶段
UI / 功能测试UI Test 后端确认没问题了，再测界面和交互

注意第二个节点——接口文档评审。这是接口测试岗特有的、也是能体现价值的地方：接口文档本身就可能有歧义，"这个字段必填吗""为空返回什么""超长了怎么处理"，在开发动手之前问清楚，成本最低。

关键认知：接口测试是把一部分测试工作往流程上游挪的手段。没有它，测试只能等前端页面做完才能开始；有了它，后端提测当天就能发现问题，可能比原来早一周。你在这上面花的力气，本质是在压缩问题暴露的时间。

2.3 接口测试能测什么、不能测什么

这一节是"边界感"，面试官问你"接口测试能不能完全替代 UI 测试"，答不上来就说明你只是会点按钮：

内容
能测业务逻辑正确性、参数校验（必填/类型/长度/格式）、边界值、异常处理与错误码、权限与鉴权（越权访问）、数据一致性（接口返回 vs 数据库）、幂等性、并发场景、性能（简单压测）、兼容性（不同版本的接口共存）
不能测页面布局与样式、交互体验（动画、loading 状态、提示文案位置）、浏览器兼容性、前端表单校验（前端不校验也不影响接口，但用户能感知）、图片渲染、前端路由

其中有两个词你要专门记住，因为它们是接口测试的"特产"，UI 测试很难做：

  • 越权访问：拿 A 用户的 token 去查 B 用户的订单。UI 上你可能看不到这个入口，但接口层面直接就能调。这是接口测试最能出彩的地方，也是常见的安全漏洞。
  • 幂等性：同一个下单请求发两遍，会不会生成两笔订单。UI 上你手再快也难复现，接口上连点两次就行了。

面试如果问"接口测试能替代 UI 测试吗"，正确答法：不能替代，是互补。接口测试覆盖后端逻辑、执行快、适合回归；UI 测试覆盖用户可见的交互和样式，是最后一道验收。合理的策略是接口层覆盖大部分逻辑，UI 层只覆盖核心业务流程。

2.4 本讲的自测题

Q1：你为什么做接口测试？

要点：三个优势 —— 介入早、执行快且稳定、定位准，最后收在"所以我们用测试金字塔，接口层做主要覆盖，UI 层覆盖核心流程"。不要只说"因为快"。

Q2：接口测试能完全替代 UI 测试吗？

要点：不能。接口测不到页面渲染、交互体验、前端校验、浏览器兼容性。二者互补：接口管逻辑，UI 管体验。

Q3：什么事情是接口测试能做、UI 测试很难做的？

要点：越权访问（用别人的身份访问数据）、幂等性（重复请求）、参数边界（UI 上根本输不进去的极值）、错误码校验、并发。答出任意两个并说清为什么，就算过关。

3动手：Postman 从裸装到用顺

这一讲是"手上动作"。配合附录 D 的公开 API 一起做，边看边点。

3.1 装什么、怎么装

Postman 是免费客户端，官网直接下载 Windows 版，一路下一步即可。装完之后可以跳过登录（会提示你注册，直接找"Skip"或关掉窗口），本地使用完全不受影响。

为什么不建议直接用网页版：网页版功能受限，且跨域请求常报错。装桌面客户端。

如果你暂时不想装软件：Apifox、Hoppscotch（网页版，免安装）都能完成这份路径里 90% 的操作。工具不是重点，见附录 B。

3.2 界面就是第 1 讲那张图

打开 Postman 新建一个请求，你会看到：

界面元素对应第 1 讲的哪个部分
左上角的方法下拉框（GET）请求方法 Method
旁边的地址输入框域名 + 路径 Path
Params 标签页查询参数 Query（会自动拼到地址后面）
Authorization 标签页认证（token / 账号密码）
Headers 标签页请求头（Content-Type 在这里设）
Body 标签页请求体（选 raw → JSON）
下方响应区状态码 + 响应体 + 响应头 + 耗时

看到这张对应表，你应该意识到 Postman 没什么神秘的——它只是把第 1 讲那张解剖图做成了输入框。第 1 讲理解了，这一讲就只剩熟悉位置。

3.3 你的第一个请求

用附录 D 里的公开 API 试一次。这个接口是最经典的练手对象：

  1. 方法选 GET
  2. 地址填 https://jsonplaceholder.typicode.com/posts/1
  3. 点 Send
  4. 看下方：状态码是不是 200，返回体是不是一条带 id、title、body 的 JSON

成功之后，把方法改成 POST，地址还是这个，切到 Body → 选 raw → 右边格式选 JSON，填：{"title":"test","body":"hello","userId":1}，再 Send。

注意对比两次的状态码：GET 返回 200，POST 成功创建应该返回 201。这就是第 1 讲状态码那一节说的"更精确的返回"。

3.4 Collection：把散落的请求收进抽屉

发过几个请求之后，你需要一个地方存放它们——就是 Collection（集合）。

对应到测试工作里，Collection 就是你的"接口用例集"。典型的组织方式是按模块分文件夹：

层级例子对应现实
Collection练手项目 API一个被测系统
Folder用户模块 / 订单模块功能模块
Request登录、查用户详情、创建订单一条接口用例
Request 内的多个示例登录-成功 / 登录-密码错误 / 登录-账号不存在同一条接口的不同用例

面试可以这么说："我会按模块组织 Collection，一个接口下面挂多条用例，涵盖正常流、参数异常和权限异常。"这句话说出来，面试官就知道你不是随便点点。

3.5 环境变量：接口测试的效率核心

这是 Postman 最值得学的一个功能，因为它是回归测试能跑起来的前提。

问题：你本来在测试环境 https://test.example.com 测得好好的，现在要切到预发环境 https://pre.example.com。难道把 50 条请求的地址一条条改？

解法：把会变的东西抽成变量。

类型作用范围典型用途
Global整个 Postman不太用，容易污染
Environment选中的那套环境最常用：区分测试/预发/生产
Collection这个集合内该集合共用的常量
Local单次运行临时值

用法：建一个环境，里面定义 baseUrl = https://jsonplaceholder.typicode.com，然后把请求地址写成 {{baseUrl}}/posts/1。切换环境时只要在右上角换个下拉框，所有请求的地址一起变。

哪些东西适合做成变量：域名（baseUrl）、token、固定的测试账号、经常变动的 userId / orderId。

更关键的一步：token 可以是自动写进去的——在登录请求的 Tests 标签里写一行脚本，把响应里的 token 存进变量，后面的请求自动带上。详见第 4 讲。

3.6 Collection Runner：一次跑完一批用例

一条条点 Send 叫"手工调用"。真正体现价值的是批量执行：点一下，整个 Collection 里几十条用例全跑完，最后给你一张结果表——多少通过、多少失败。

操作路径：Collection 上点 Run（或 ... → Run collection）→ 选环境 → 设迭代次数 → Start。

这就是"回归测试"的雏形。面试问"你们的接口回归怎么做的"，你可以答："用 Collection Runner 批量跑整个集合，配合断言自动判定通过与否，每次版本发布前跑一遍。"

3.7 导入接口文档：不用手敲

真实工作里没人手敲接口地址。接口文档（Swagger / OpenAPI 格式）可以直接导入 Postman，自动生成整个 Collection 的骨架。

公司里常见的流程是：开发用 Swagger 维护接口文档 → 你导出 OpenAPI 文件 → 导入 Postman → 补上环境变量和断言 → 变成可跑的用例集。

3.8 本讲的自测题

Q1：Postman 里的环境和变量有什么用？

要点：把会变的部分（域名、token、测试账号、动态 ID）抽出来，一次配置多处复用、切换环境不用改请求。补一句"这是接口用例能从"只能手工点"变成"能批量跑"的前提"。

Q2：你怎么组织你的接口用例？

要点：Collection 按系统，Folder 按模块，一个请求下挂多条用例覆盖正常流、参数异常、权限异常。不要说"就存在一个列表里"。

Q3：一条条手工点，怎么变成批量回归？

要点：给每条请求写断言（第 4 讲）→ 用 Collection Runner 批量执行 → 看结果报告。关键在断言——没有断言，批量跑出来的结果没有意义，因为你不知道哪条过了。

4断言：让请求自己判断对错（面试最重）

这一讲是整份路径的核心。前面三讲都是为了让你在这里能"理解"而不是"背诵"。

4.1 为什么必须有断言

先把最根本的问题问清楚：你怎么知道一个接口是"通过"了？

新手答案：看状态码是不是 200。

正确答案：200 只说明网络通了，不说明业务对了。考虑这几种情况——

情况状态码实际情况
查订单列表，返回 {"list":[]}200接口坏的，或者查错了人的数据
创建订单，返回 {"orderId": null}200订单根本没建出来
查询用户，余额返回 "balance": "-1"200金额算错了，是线上事故级 bug
返回条数只有 5 条，数据库里有 23 条200分页逻辑坏了
金额字段返回的是字符串 "100" 而不是数字 100200类型不对，前端可能直接崩

这五种情况，只看状态码全都"通过"，实际全是 bug。所以"测过了"的标准不能是"状态码 200"，必须是对响应内容逐项做了校验。这就是断言。

面试标准答法："我不会只看状态码。状态码只能说明 HTTP 层通了，我会在 Postman 的 Tests 里写断言——校验状态码、关键业务字段的值、字段的数据类型、以及数组的条数，必要时再查数据库核对数据。只有断言全过了，这条用例才算通过。"

这段话是这份路径里信息量最大的一句面试话术。它同时证明了：你懂 HTTP 分层的局限、你会用工具、你有测试思维、你知道怎么判定通过。

4.2 Postman 的断言写在哪、长什么样

断言写在请求的 Tests 标签页里（不是 Pre-request Script，那个是发送前跑的）。语法是基于 JavaScript 的，但你不用会 JS，记住几个固定句式就行。

一个最基础的断言长这样：

pm.test("状态码应该是 200", function () { pm.response.to.have.status(200); });

把它拆成三块看：

部分含义
pm.test("名称", function(){...})定义一个断言，引号里的名称就是报告里显示的那行字
函数体里的判断真正要校验什么
pm.response代表这次的响应对象，你的数据都从它身上取

记住这个心智模型：你是在写"我期望什么"，而不是"我要做什么"。写断言的过程，就是把你心里的验收标准翻译成机器能判断的语句。

4.3 常用的四类断言（够用 90%）

下面是真正会天天用到的，背下来：

要校验什么写法
状态码pm.response.to.have.status(200);
响应时间pm.expect(pm.response.responseTime).to.be.below(1000);
某字段等于某值pm.expect(jsonData.userId).to.eql(1);
某字段存在且不为空pm.expect(jsonData.title).to.be.a("string").and.not.empty;
某字段是数字类型pm.expect(jsonData.id).to.be.a("number");
数组长度pm.expect(jsonData.length).to.eql(100);
包含某段文本pm.expect(pm.response.text()).to.include("成功");

其中 jsonData 是 Postman 里约定的变量名，先解析响应体再用：

var jsonData = pm.response.json();

这两行要连起来看：第一行把响应体转成能点属性出来的对象，第二行才能写 jsonData.字段名。

区分 eql 和 equal：这是新手容易混的地方。eql 是宽松比较，1 == "1" 也认为相等；equal 是严格比较，类型也要一致。测接口字段类型时要用严格的那个，否则 "100" 和 100 分不出来，而它们对前端是两种东西。

4.4 断言实战：一段能直接用的完整代码

假设你在测"查询一条帖子"，地址是 {{baseUrl}}/posts/1，把下面整段贴进 Tests 标签页：

var jsonData = pm.response.json();

pm.test("状态码是 200", function () { pm.response.to.have.status(200); });

pm.test("id 是数字 1", function () { pm.expect(jsonData.id).to.eql(1); });

pm.test("title 是非空字符串", function () { pm.expect(jsonData.title).to.be.a("string").and.not.empty; });

pm.test("userId 字段存在", function () { pm.expect(jsonData).to.have.property("userId"); });

pm.test("响应时间小于 1 秒", function () { pm.expect(pm.response.responseTime).to.be.below(1000); });

点 Send，切到 Test Results 标签页，你会看到 5 行结果，每行前面一个绿勾。这就是"一条真正测过了的接口用例"。

现在故意把地址改成 {{baseUrl}}/posts/999999（不存在的 ID），再 Send——你会看到有的断言变红，因为 id 不等于 1 了。这一步很有价值：你要亲眼看到断言能失败，否则你不知道它有没有在起作用。

4.5 顺手把 token 自动化：变量提取

前面说过 token 要手工填很麻烦。用断言区里的脚本可以自动存：

var jsonData = pm.response.json();

pm.environment.set("token", jsonData.token);

第一行解析响应，第二行把响应里的 token 存进环境变量。之后在别的请求的 Authorization 里引用 {{token}} 就行，登录一次，全集合的请求自动带上新 token。

这解决了一个真实痛点：token 过期了，只要重跑一下登录请求，其他用例不用动。这就是第 3 讲说的"环境变量是效率核心"的落地方式。

4.6 数据驱动：同一接口跑不同参数

如果一条接口要用 20 组参数测 20 遍，不要复制 20 个请求。做法是：

  1. 把参数写成 {{username}} 这样的变量
  2. 准备一个 CSV 或 JSON 文件，每行一组数据
  3. Collection Runner 里选择这个数据文件
  4. Runner 会按行迭代，每行跑一次整批请求

这个技术叫数据驱动测试。面试提到这个词就是加分项——它说明你考虑过"怎么高效地覆盖多组数据"，而不是靠体力。

4.7 本讲的自测题

写下你对这 5 题的答案，再展开对照

Q1：接口返回 200，你怎么判断这个接口通了？

要点：不能只凭 200。要写断言校验——状态码、关键业务字段的值、字段类型、数组条数、响应时间。必要时还要查数据库核对数据。答完补一句"状态码只代表 HTTP 层通了"。

Q2：断言一般验哪些内容？

要点：① 状态码；② 业务字段的值是否符合预期；③ 字段的数据类型（数字还是字符串）；④ 字段是否存在、是否为空；⑤ 列表返回的条数；⑥ 响应时间。按这个顺序说，逻辑清楚。

Q3：登录接口返回的 token，怎么让后续请求自动带上？

要点：在登录请求的 Tests 里用 pm.environment.set 把 token 存成环境变量，后续请求用 {{token}} 引用。好处是 token 过期只需重跑登录。

Q4：同一条接口要测 20 组参数，你会怎么做？

要点：数据驱动。参数用变量占位，准备 CSV / JSON 数据文件，用 Collection Runner 迭代执行。不要答"复制 20 个请求"。

Q5：你写的接口用例，怎么判断是"通过"还是"失败"？

要点：靠断言自动判定，不是靠人眼。写了断言的用例，Runner 会给出通过/失败统计；没写断言的用例，批量执行结果是不可信的。这句话能体现你理解自动化的前提。

这一讲最容易踩的坑：把断言当成"高级功能"跳过，只学怎么发请求。结果就是——你会用 Postman，但不会做接口测试。面试时"你怎么判断接口测过了"这一题会直接把你打回原形。断言是接口测试和接口调用的分界线。

5设计：接口用例怎么想出来

工具会用了，接下来是真正决定水平的部分：测什么。

5.1 先看接口文档，再动手

拿到一条接口，先别急着发请求。把文档上这几项读清楚：

要看什么为什么
接口地址与方法决定你在 Postman 里怎么填
请求参数：必填还是选填、类型、长度限制这直接决定你要设计哪些用例
响应字段和含义决定你的断言写什么
错误码列表决定异常用例的期望结果
是否需要鉴权、什么角色能调决定权限用例

文档没写清楚的地方，就是你要提问的地方。"这个字段必填吗""为空返回什么""超长了报什么错"——在开发动手前问清楚，比测出来打回去改便宜得多。这也是第 2 讲说的"接口文档评审"节点的价值。

5.2 一条接口的标准用例矩阵

这是本节的核心。拿到任何一条接口，按下面这六类去思考，基本不会漏：

类别测什么以"创建订单"接口为例
① 正常流所有参数都合法，业务能走通商品有效、库存充足、金额正确，下单成功，返回订单号
② 参数校验必填、类型、长度、格式不传商品 ID → 400；金额传 "abc" → 400；数量传 0 或负数 → 400
③ 边界值刚好在边界和越过边界数量 = 1（最小值）、= 库存数（最大值）、= 库存数 + 1（越界）
④ 业务规则业务逻辑的约束条件库存不足、商品已下架、优惠券已过期、余额不够
⑤ 权限与鉴权不同身份能做什么不带 token → 401；普通用户调管理接口 → 403；用 A 的 token 操作 B 的订单 → 应被拒绝
⑥ 异常与幂等重复提交、并发、服务异常同一请求连发两次 → 只生成一笔订单；网络超时后的处理

这张表就是面试题"一条接口你会怎么测"的答案。很多人只会答"测正常和异常"，这两句太虚。按上面六类说出来，每类举一个具体例子，面试官立刻知道你是真的设计过用例。

5.3 参数校验用到的两个方法

方法本身你在测试基础里学过，这里只说怎么用到接口上：

方法接口测试里的用法
等价类划分把参数取值分成"有效等价类"和"无效等价类"。比如年龄 1–100 有效，那么 -1、0、101 属于无效类，取代表值即可，不用穷举
边界值分析错误最常出在边界上。年龄 1–100，必测 0、1、2、99、100、101 这几个点

再补一个接口特有的问题：参数不传（字段直接没有）和参数传空（""）和参数传 null，是三件不同的事，后端处理逻辑经常不一样。这三个都要测——这是接口测试比 UI 测试更细的地方，因为 UI 上你没法制造"字段不存在"这种请求。

5.4 账号与数据的准备

接口测试有一个 UI 测试没有的麻烦：你得自己准备数据。没有登录态你什么都测不了，没有可用的商品 ID 你下不了单。

要准备什么说明
测试账号（多个角色）普通用户、管理员各一个，权限用例要用
有效的 token通过调登录接口拿，用第 4 讲的方法自动存
基础数据能用来下单的商品、有余额的账户
数据清理的考虑下单会造脏数据，测试库要能重置

一个真实经验的细节：涉及金额的接口，测试账号的余额最好充足，否则测到一半报"余额不足"，你分不清是 bug 还是数据没了。这种"环境准备不足导致误判"的经历，在面试里讲出来很真实。

5.5 本讲的自测题

Q1：给你一条接口，你会设计哪些测试用例？

要点：按 5.2 的六类说 —— 正常流、参数校验、边界值、业务规则、权限鉴权、异常与幂等，每类举一个具体例子。这个答案的结构本身就是加分项。

Q2：接口参数校验你会测什么？

要点：必填不传、类型错误、长度超限、格式错误（手机号/邮箱/日期）；特别补一句"参数不传、传空字符串、传 null 要分别测，后端处理常常不一样"。

Q3：你会怎么测权限？

要点：三种 —— 不带 token（期望 401）、低权限账号访问高权限接口（期望 403）、越权访问（用 A 的身份访问 B 的数据，期望被拒绝）。最后这个是接口测试才能做的，要主动说出来。

Q4：什么是幂等？你会怎么测？

要点：同一个请求执行多次，结果应该和执行一次一样。测法：把同一个下单请求连发两次，检查是否只生成一笔订单。UI 上很难这么做，接口上很容易——这是接口测试的优势。

6话术：面试怎么讲

知识有了，还得能说得像做过的人。这一讲是包装，不是编造。

6.1 30 秒讲清你怎么做接口测试

被问到"你平时怎么做接口测试"时，用这条线讲，不要东一句西一句：

"后端接口提测后我就介入，比 UI 测试早一个阶段。我的流程是三步：先按接口文档和验收标准设计用例，再在 Postman 里按模块组织成 Collection，最后用 Collection Runner 批量执行并出结果。"

"用例设计上，我一般覆盖六类：正常流、参数校验、边界值、业务规则、权限鉴权，还有幂等和异常场景。参数这块我会专门测必填缺失、类型错误、长度超限，还有参数不传、传空串、传 null 三种情况——后端对这三者的处理经常不一样。"

"判定通过上，我不会只看状态码。200 只说明 HTTP 层通了，我会在 Tests 里写断言，校验状态码、关键业务字段的值、字段类型和列表条数；涉及金额或库存的接口，我还会去数据库核对一下数据是不是真的落库了。"

这段话里加粗的部分，是让它听起来"像做过"的关键：明确的介入时机、结构化的用例分类、对参数细节的具体认知、以及对"200 不算通过"的敏感度。

6.2 用 STAR 讲一个接口 Bug 案例

结构说什么示例
S 情境什么版本、什么功能"上个版本做结算功能，我负责结算相关接口的测试"
T 任务你负责什么"我负责金额计算和优惠券叠加这两个接口"
A 行动重点：你怎么发现的、怎么定位的、怎么跟进的"我按等价类划出 6 组金额场景批量跑，发现当优惠券面额大于订单金额时，接口返回的实付金额是负数，但状态码是 200。我先确认必现，然后把请求和响应截图、加上复现步骤写进单子，同时去数据库核对了落库金额——库里的值也是负的，说明是后端计算逻辑的问题，不是前端展示问题。据此指派给了结算模块的开发"
R 结果最后怎么样、你学到什么"开发当天修复。我回归通过后，把这组场景补成了固定用例，后来又加进了自动化回归集。这件事让我意识到光看状态码是不够的，必须对关键字段做断言"

注意行动部分：批量跑、确认必现、查数据库区分前后端、附请求响应——这四个细节就是"专业度"的证明，比说"我很细心"有用得多。

6.3 三个千万不能说的回答

不要说为什么改成
"我看到返回 200 就说明接口没问题"暴露你不知道 HTTP 分层，也不做断言"200 只代表 HTTP 层通了，我会对响应体里的关键字段写断言，必要时查数据库核对"
"接口测试就是拿 Postman 点一点"把工具当成了方法"Postman 是执行工具，接口测试的核心是用例设计——按正常流、参数、边界、权限、幂等这几个维度去覆盖"
"接口测试可以替代 UI 测试"不懂测试分层"两者互补。接口测后端逻辑，快且稳，适合回归；UI 测用户能看到的交互和样式。我们的策略是接口层做主要覆盖，UI 层覆盖核心流程"

6.4 如果被问到不会的

比如"你用过 JMeter 吗""你们的接口自动化是怎么接 CI 的"。不要编。用这个句式：

"这个我没实际用过。不过我知道它是解决 X 问题的，我目前的做法是 Y，思路是通的。如果有需要，我可以很快上手。"

面试官对"承认不会 + 说清理解 + 给出替代做法"的容忍度，远高于"编一个被追问两句就穿帮的答案"。

D练习环境：零成本公开 API

接口测试必须有个真实的被测对象。下面这些免费、免注册、随时能打开。

主力选择：JSONPlaceholder

一个假的在线 REST API，提供 posts / comments / users / todos 等资源，支持完整的 CRUD，非常适合练手。

用途请求
查列表GET https://jsonplaceholder.typicode.com/posts
查单条GET https://jsonplaceholder.typicode.com/posts/1
新增POST https://jsonplaceholder.typicode.com/posts
更新PUT https://jsonplaceholder.typicode.com/posts/1
删除DELETE https://jsonplaceholder.typicode.com/posts/1
嵌套资源GET https://jsonplaceholder.typicode.com/posts/1/comments

注意它的局限：它是模拟服务，POST / PUT / DELETE 不会真的改数据，但会返回成功和相应的结构。这完全不影响你练发送请求、设请求头、写断言、跑批量。你的目标是练"测的动作和判定方法"，不是验证它的业务逻辑。

补充选择：httpbin

专门用来"把请求原样回显给你"，是理解请求结构的最佳工具。你不知道自己的请求到底长什么样时，用它照一照。

用途请求你会看到
回显请求GET https://httpbin.org/get你发出去的头、参数、来源 IP
回显 POSTPOST https://httpbin.org/post你提交的 body 原样返回
指定状态码GET https://httpbin.org/status/404返回 404，用来练断言失败的样子
模拟延迟GET https://httpbin.org/delay/3延迟 3 秒，用来练响应时间断言
需要鉴权GET https://httpbin.org/basic-auth/user/pass用来练 Authorization 的填法

重点推荐 /status/404 和 /delay/3 这两个——它们能让你亲手制造"断言失败"的场面，看到红色的叉长什么样。只见过绿勾的人，不会写有效的断言。

三个练习动作（配合第 3、4 讲）

  1. 建一个 Collection，叫"练手 API"，里面分两个 folder：JSONPlaceholder 和 httpbin，把上面这些请求都存进去
  2. 建一个环境，定义 baseUrl，把所有请求的地址改成 {{baseUrl}} 形式
  3. 给每条请求写断言，然后打开 Runner 批量跑一遍，看结果报告里有多少绿勾。跑通之后，故意改坏一条断言，再跑一次，看红色的样子

本讲的完成标准：不看任何资料，能在 30 分钟内完成三件事——① 用 Postman 发一个带 JSON 请求体的 POST 请求并让状态码返回 201；② 给一条 GET 请求写出至少 4 条断言（状态码、字段值、字段类型、响应时间）；③ 用 Collection Runner 批量跑完一个包含 5 条请求的集合，并说出哪几条失败、为什么失败。
